# Ship Live

Shipping live is mostly an environment-parity problem plus a buyer-safety problem.

## Before you launch

Make sure all of this is true:

- the change is on a focused branch from `main`
- the pull request targets `main`
- feature branches have already proven code correctness in PR checks
- the marketing page is clear enough to buy from
- auth works in the real deployed environment
- checkout returns to the deployed `/checkout/success`
- the live webhook is registered and verified
- newly paid users reach `/workspace/choose`, and returning generated-codebase users reach `/codebase`
- the first protected flow is usable after access appears

## Production checklist

1. Open a focused pull request from your feature branch into `main`.
2. Run the narrowest relevant local checks from the repo root before opening the PR, and use `bun run check` when the release slice justifies a full local pass. PR CI is the required merge gate; the repository does not install git hooks that block commits or pushes.
3. Merge only after required GitHub checks pass.
4. Confirm Vercel creates the production web deploy from `main`.
5. Confirm GitHub Actions runs `Convex Production Deploy` for the same `main` merge, or records an intentional skip when automatic deploys are paused.
6. Let GitHub Actions run `Production Release Proof` against the exact Vercel production deployment for the merged commit and then against the public site after the release lands.
7. Register or verify the live Stripe webhook endpoint.
8. Confirm product-access grant happens in the deployed environment, not just locally.
9. Confirm the buyer reaches the protected product after payment.

`Production Release Proof` is the primary post-merge browser gate for this repo. It should always run the hosted `default_ship` pass against the canonical production URL, loading production auth and Convex values from `QA_ENV_FILE=apps/web/.env.production`. When the merged release changed checkout, Stripe, entitlement, webhook, or access handoff behavior, that workflow should also run the hosted `billing_integration` pass automatically instead of waiting for someone to remember an opt-in rerun.

Retired staging aliases are no longer release-candidate authority. Use feature-branch previews for inspection and use `main` production proof as the release evidence.

The production proof bootstrap does not require a separate `CONVEX_DEPLOYMENT` line in `apps/web/.env.production`. It derives the production deployment target from `NEXT_PUBLIC_CONVEX_URL` when needed, so the important thing is keeping the production env file truthful to the live Clerk and Convex environment.

For this repo, the safest staging or production billing proof is a live no-cost Checkout run using a restricted `100% off` promotion code:

- single-use when possible
- short expiry
- restricted to the QA customer if possible

That verifies the part we actually care about in staging or production:

- Checkout Session creation
- hosted Checkout completion
- redirect into `/checkout/success`
- live Stripe webhook delivery
- Convex product-access grant
- redirect into `/workspace/choose`

It does **not** prove live card charging or decline behavior. Keep card-path confidence in sandbox or local Stripe testing.

The live Stripe webhook must target the Convex HTTP-actions route, not the app origin:

`https://<your-convex-production-deployment>.convex.site/stripe/webhook`

Before trusting production billing, verify `STRIPE_WEBHOOK_SECRET`, `CHECKOUT_FULFILLMENT_RETRY_SECRET`, and `STRIPE_SECRET_KEY` on the production Convex deployment. Use the internal observability runbook for the incident-control drill and Telegram delivery checks.

After those are correct, let the hosted `billing_integration` run prove one fresh live no-cost order and verify it auto-forwards through passwordless sign-in into `/workspace/choose` without replaying the Stripe event. On production, that proof should create the Checkout Session directly with a fresh one-time `100% off` coupon already attached instead of depending on manual promotion-code entry inside Stripe’s hosted UI. The replay path is a valid repair tool, but the clean production proof is the automatic delivery path.

## Keep these in mind

- This repo currently assumes the buyer can receive the one-time code for the Stripe checkout email before entering the paid workspace.
- If you change auth apps, webhook secrets, or Stripe accounts, re-verify the handoff instead of assuming it still works.
- Hotfixes are allowed to merge into `main`, but they must come from a focused hotfix branch and pass the same production proof as ordinary releases.
- If a hotfix changes proof/bootstrap behavior, wait for the new `Production Release Proof` run on the hotfix commit instead of trusting the failed run on the previous `main` head.
- Dedicated Convex-backed preview environments are not part of this release workflow yet. Non-`main` Vercel branches stay frontend previews only.
- Do not promise a support or access path in public copy unless it actually exists.

## What success looks like

Production is ready when a brand-new buyer can understand the offer, buy cleanly, get access without confusion, and start the product immediately, and when the release can be traced cleanly back to the `main` merge that triggered both the Vercel production deploy and the Convex production deploy.
