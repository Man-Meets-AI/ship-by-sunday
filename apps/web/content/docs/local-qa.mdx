# Local QA

Use this page as the main local verification runbook for the starter.

## Fast code checks

Use these for normal implementation work:

```bash
bun run lint
bun run format:check
bun run test:unit
bun run test:contracts
bun run test:integration
bun run build
```

For the full repo gate:

```bash
bun run check
```

## Shared Clerk QA accounts

Use two real users:

- no-access user for sign-in, `/codebase`, wrong-account, and pre-purchase checks
- granted-access user for `/codebase`, `/review`, `/settings`, and the optional `/execute`, `/mission`, and `/lesson/*` bonus-route checks after review unlock

Commands:

```bash
bun run clerk:test-user:check
bun run clerk:test-user:create
bun run clerk:test-user:check:entitled
bun run clerk:test-user:create:entitled
bun run clerk:test-user:prepare:entitled
```

`bun run clerk:test-user:prepare:entitled` is the fastest path when your hosted Convex dev deployment is already synced into `apps/web/.env.local`, because it creates the entitled Clerk QA user if needed and grants product access on the active hosted dev deployment.

Use `bun run release:personas:prepare -- --proof=<proof>` when you need the release-owned multi-persona path instead of the one-user local shortcut. The fast helper is for a single entitled debug account. The release command is the durable multi-persona setup path used by hosted proofs.

The Playwright sandbox bootstrap is a local test convenience, not a stable auth path. It seeds browser storage state for deterministic personas, but local auth still depends on Clerk syncing into the browser runtime. If the no-access browser lane ever starts behaving like an entitled user, or a signed-in lane flashes `Unauthorized` during hydration, treat that as Convex deployment drift or bootstrap failure first, not as a product-state bug.

The canonical release proof credentials live in ignored `tmp/release-personas.local.json`, or in the file named by `RELEASE_PERSONAS_LOCAL_FILE`. The release proof commands and the Playwright sandbox bootstrap both read that file for the no-access and entitled account emails and passwords.

## Full paid local handoff

Use this only in a safe local test environment.

1. Start the app against your hosted Convex dev deployment.
2. Start the Stripe listener.
3. If the listener prints a fresh webhook secret, restart the web app.
4. Sign in with the no-access account.
5. Start checkout from the landing page.
6. Complete payment with Stripe test card `4242 4242 4242 4242`, any future expiry, any CVC, ZIP `10001`.
7. Confirm Stripe returns to `/checkout/success?session_id=...`.
8. Confirm the webhook grants access.
9. Confirm the app redirects into `/codebase`.

On a new machine or after switching deployments, run `bun run dev:convex` first so `apps/web/.env.local` contains the current `NEXT_PUBLIC_CONVEX_URL`, `NEXT_PUBLIC_CONVEX_SITE_URL`, and `CONVEX_DEPLOYMENT` values. In this repo, the Stripe listener must forward to `{NEXT_PUBLIC_CONVEX_SITE_URL}/stripe/webhook`, not the `.convex.cloud` client origin.

Before you trust a local billing run, check the pinned Stripe CLI guardrail once:

```bash
bun run stripe:dev:doctor
```

That command compares the app Stripe account from `apps/web/.env.local` against the repo-owned Stripe CLI project `ship-by-sunday`. If it tells you the profile is missing or mismatched, repair it with `stripe login --project-name ship-by-sunday`. The billing flow can still be env-correct while the CLI profile is noisy, but the repo now treats that as a warning you should resolve before blaming auth or webhooks.

The easiest way to run the full buyer-flow stack after that is:

```bash
bun run dev
```

The current scripted proof for the paid handoff is:

```bash
QA_ALLOW_BILLING_INTEGRATION=1 PLAYWRIGHT_USE_LOCAL_SERVER=0 PLAYWRIGHT_BASE_URL=http://localhost:3000 bun run release:proof -- --proof=billing_integration
```

For local targets, the billing pack now runs `bun run stripe:dev:doctor` as a warning-only preflight and `bun run stripe:dev:verify` as the hard post-checkout proof after the sandbox billing journey finishes.

## Hosted and production QA

For any non-local target, keep these boundaries straight:

- `tmp/release-personas.local.json` holds the release proof email and password pairs by default.
- `apps/web/.env.local` or `QA_ENV_FILE=<path>` selects the Clerk and Convex environment where those personas will be created or reused.
- `PLAYWRIGHT_BASE_URL=<target>` selects the site the browser tests will hit.

Use the root release proof commands for hosted runs instead of stitching Playwright calls together by hand.

Hosted production example:

```bash
PLAYWRIGHT_BASE_URL=https://<production-url> QA_ENV_FILE=apps/web/.env.production bun run release:proof -- --proof=default_ship
```

If the loaded Clerk env does not match the hosted target, persona prep now fails immediately with a Clerk publishable-key mismatch. That is intentional. Fix the env selection before treating any authenticated browser failure as an app bug.

## Recommended flow checks

For public pages, crawl metadata, auth noindex, and checkout recovery, use source-level tests instead of the retired shallow browser proof lane:

```bash
bun run --cwd apps/web test:unit -- public-metadata route-metadata home-page structured-data
bun run --cwd apps/web test:integration:ui -- checkout-success home-page-primary-cta
```

Run `bun run test:integration` from the repository root when the change touches shared app routing or public metadata broadly.

### Canonical protected-route smoke

1. Visit `/codebase` while signed out.
2. Confirm redirect into `/sign-in` with `/codebase` preserved in `redirect_url`.
3. Visit `/review` while signed out.
4. Confirm redirect into `/sign-in` with `/review` preserved in `redirect_url`.

### Identity route smoke

1. Open `/sign-in` with no query params and confirm the branded split shell renders with the quiet `See pricing` path.
2. Open `/sign-in?redirect_url=%2Fsettings` and confirm the same shell renders but the pricing path is hidden because the route is in recovery mode.
3. Open `/session-tasks/reset-password` and confirm the route keeps the same branded shell while leaving the Clerk reset form itself intact.

### No-access flow

1. Sign in with the no-access account.
2. Visit `/codebase`.
3. Confirm the page explains that the account has no active access and shows which email is currently signed in before you treat it as a Stripe or Convex failure.

### Granted-access flow

1. Run `bun run review:handoff:doctor` before the browser checks so the route and handoff contract are green before you spend time on auth or playback issues.
2. If you intend to use the local-auth browser lane, treat it as a convenience path only. The stable shared proof remains the sandbox browser path.
3. Run `bun run clerk:test-user:prepare:entitled`.
4. Sign in with the granted-access account.
5. Confirm `/codebase`, `/review`, and `/settings` load.
6. On `/review`, confirm the page makes one automatic Ship by Sunday Codebase download attempt, keeps the fallback download link visible if the browser blocks it, and does not present a manual download dashboard.
7. On `/review`, confirm the fallback link text is `Need the Ship by Sunday Codebase again? Download it here.` on a normal revisit, and that direct `/review` visits do not auto-start another download.
8. From `/review`, confirm the primary CTA opens lesson `3.1`.
9. Before unlocking Execute / Ship, confirm direct `/mission` and `/lesson/<route-segment>` visits show explicit locked-bonus messaging instead of forwarding into `/codebase`.
10. Confirm `/mission` loads as the bonus library with the top block rail in natural `Product -> Design -> Build -> Ship` order, defaulting the active block to Build.
11. Confirm direct `/lesson/<route-segment>` visits render the restored video-first bonus lesson path with the top block rail plus the bottom lesson skill rail, and without workbench inputs.

### Legacy redirect QA

1. Run `bun run clerk:test-user:prepare:entitled`.
2. Visit `/start`.
3. Confirm it forwards to `/codebase`.
4. Visit `/product`, `/design`, `/marketing`, and `/build-plan`.
5. Confirm each route forwards to the matching `/codebase#<section>` anchor.
6. Visit `/artifacts`.
7. Confirm it forwards to `/review`.

## Observability smoke

Use this only for maintainer-level incident work. The full webhook, incident-control, and Telegram-delivery drill now lives in the internal observability runbook, so this page stays focused on local QA flows instead of repeating that same path.

## What success looks like

You are done when the app passes all four realities:

- signed out
- signed in without access
- signed in with granted access
- newly paid and waiting for access grant

Anything less is partial confidence, not real QA.
