# Clerk + Convex Auth

This is the most important setup page in the starter.

If Clerk and Convex do not agree on the `convex` JWT template and issuer, the app can sign users in while protected server-side reads still fail.

## Required env values

Make sure `apps/web/.env.local` has these values:

```bash
NEXT_PUBLIC_CLERK_PUBLISHABLE_KEY=
NEXT_PUBLIC_CLERK_SIGN_IN_URL=/sign-in
NEXT_PUBLIC_CLERK_SIGN_IN_FALLBACK_REDIRECT_URL=/codebase
NEXT_PUBLIC_CLERK_SIGN_UP_FALLBACK_REDIRECT_URL=/codebase
CLERK_SECRET_KEY=
CLERK_FRONTEND_API_URL=
CLERK_AUTHORIZED_PARTIES=http://localhost:3000
NEXT_PUBLIC_CONVEX_URL=
```

`NEXT_PUBLIC_CONVEX_URL` comes from the Convex tooling once you run `bun run dev:convex`. That command also writes `CONVEX_DEPLOYMENT` into `apps/web/.env.local` so the repo scripts and `convex run` commands target your hosted dev deployment explicitly.

## Clerk setup

1. Create a Clerk app.
2. Copy `NEXT_PUBLIC_CLERK_PUBLISHABLE_KEY`, `CLERK_SECRET_KEY`, and `CLERK_FRONTEND_API_URL`.
3. If you keep the starter’s custom login page, set `NEXT_PUBLIC_CLERK_SIGN_IN_URL=/sign-in` so Clerk OAuth callbacks resolve to the right route.
4. Set the Clerk fallback redirect URLs to `/codebase` so direct visits to auth routes land in the codebase-first protected shell.
5. Keep the Clerk frontend API domain consistent everywhere you wire auth.
6. Set `CLERK_AUTHORIZED_PARTIES` to the trusted web origins that should be allowed to present Clerk session cookies.
7. In every Clerk environment used by this app, enable email sign-in with an email verification code. The checkout handoff calls Clerk email OTP for the Stripe checkout email; it does not use Google or password setup on that route. Keep password sign-in enabled only if you still want the generic `/sign-in` password form to work outside checkout.

The starter-owned auth routes are:

- `/sign-in`: the branded Ship by Sunday sign-in surface
- `/checkout/email-handoff`: the post-checkout email-code handoff for paid guest checkout
- `/session-tasks/reset-password`: the Clerk reset-password task inside the same identity shell
- `/sso-callback`: the OAuth callback completion route inside the same identity shell

`/sign-up` is not a custom starter sign-up UI in this repo. Direct visits redirect to pricing, and legacy checkout links such as `/sign-up?session_id=...` redirect to `/checkout/email-handoff`.

## Checkout email-code setup

The checkout email handoff depends on a Clerk Dashboard setting, not a new repo env var.

- Where: Clerk Dashboard for local, preview, and production Clerk applications.
- What: enable email address sign-in with email verification code.
- Callback routes: keep the app-owned sign-in URL at `/sign-in`; the checkout email-code flow itself stays on `/checkout/email-handoff` and returns to `/checkout/success?session_id=...`.
- Verify: complete a paid test checkout while signed out, click the checkout-email handoff, and confirm Clerk sends a one-time code to the Stripe checkout email.
- Missing setup looks like: the handoff page keeps the locked checkout email but Clerk cannot send or verify the email code, so the buyer cannot prove the paid email.

## The `convex` template is not optional

Inside Clerk:

1. Open your app.
2. Go to `JWT Templates`.
3. Create or confirm a template named `convex`.
4. Use `convex` as the application ID.
5. Make sure the issuer/domain matches your Clerk frontend API URL.

This starter is hard-wired to that identifier.

## Convex setup

Connect the repo to your hosted Convex dev deployment with:

```bash
bun run dev:convex
```

That flow should give you the `NEXT_PUBLIC_CONVEX_URL` value the app expects and set `CONVEX_DEPLOYMENT` for CLI-driven QA helpers. This repo does not support Convex's local backend mode as a first-class workflow, so keep the Clerk app, frontend API domain, and token-template assumptions aligned with your hosted Convex dev deployment.

Run the auth doctor any time you switch Clerk instances or Convex dev deployments:

```bash
bun run auth:dev:doctor
```

Local `bun run dev` startup now runs that same check automatically before `next dev` starts.

## What success looks like

You are correctly wired when:

- sign-in works
- sign-in from a deep link returns the user to that exact page after auth or after any Clerk task
- `/sign-in`, `/session-tasks/reset-password`, and `/sso-callback` all render cleanly in local smoke runs
- `/checkout/email-handoff` sends a Clerk email code to the Stripe checkout email and returns to `/checkout/success`
- protected routes can read server-side state
- protected pages do not throw `Unauthorized` during the first client hydration pass
- the workspace gate can tell the difference between signed-out and signed-in users
- product-access checks do not fail with a token or issuer mismatch

## Why the starter now seeds initial data on the server

Protected routes and `/checkout/success` now render from a server-fetched Convex snapshot first, then let Clerk-gated live queries take over in the browser.

That is intentional. It protects the first render from a short Clerk/Convex auth sync gap during hydration, where the browser can briefly lack a Convex identity even though the server already validated the session.

## If this breaks

Check these in order:

1. the Clerk JWT template is named exactly `convex`
2. the issuer/domain in Clerk matches the same Clerk frontend API domain used by the app
3. `NEXT_PUBLIC_CLERK_SIGN_IN_URL` is still `/sign-in`
4. `CLERK_AUTHORIZED_PARTIES` still includes the current app origin
5. `NEXT_PUBLIC_CONVEX_URL` and `CONVEX_DEPLOYMENT` are not still pointed at an old or different Convex dev deployment
6. you restarted the app after changing auth env values

For local Playwright checks, remember that the local-server flow intentionally sets `DISABLE_CLERK_MIDDLEWARE=1`. In that mode, the sign-in route must respect `shouldBypassClerkProtection()` before calling `auth()` during server render. If the check fails before any auth-route assertions run, inspect the sign-in route entrypoint and the Clerk bypass helper before treating it as a Clerk misconfiguration.

If the app is using the right local Clerk keys but hosted Convex still trusts the wrong issuer, push the current local frontend API URL into the active hosted dev deployment and rerun the doctor:

```bash
cd apps/web
./node_modules/.bin/convex env set CLERK_FRONTEND_API_URL "$CLERK_FRONTEND_API_URL"
bun run auth:dev:doctor
```

If checkout succeeds but access still fails, go straight to [Troubleshooting Stripe and Convex](/docs/troubleshooting/stripe-convex).
