# Configure the Homepage

The homepage is no longer one giant page contract. It now has a small control plane, a content layer, and a render-model layer so you can change the public shell without scattering behavior across unrelated files.

This page is the source of truth for future builders and future AI agents who need to change the homepage.

## The three layers

### 1. Starter control plane

`config/product.ts` owns the durable homepage controls under `starterConfig.homePage`.

That config currently controls:

- `sections.productPreview`
- `sections.hero`
- `sections.sprintPath`
- `sections.execLoop`
- `sections.starterSystem`
- `sections.durability`
- `sections.socialProof`
- `sections.faq`
- `sections.pricing`
- `sections.footer`
- `heroPrimaryCta`
- `pricingPrimaryCta`

The homepage also has a fixed canonical order in `homePageSectionOrder`. This is intentional. The starter supports section visibility, not a drag-and-drop page builder.

### 2. Content layer

`app/_content/home-page.ts` owns the default copy and assets.

That file should answer:

- what the homepage says
- which image assets it uses
- what FAQ items exist
- what the default social-proof content contains

That file should not decide whether a section renders.

### 3. Render model

`app/_lib/home-page-render-model.ts` combines starter config plus homepage content into the render contract used by the page.

This file is the behavioral seam. It decides:

- which sections are enabled
- which CTA target each section uses
- which social-proof subtype is active
- whether GitHub activity should be fetched

If a future agent adds homepage behavior, add it here first instead of sprinkling conditional logic through multiple components.

## Current section contract

The homepage renders these top-level sections in this fixed order:

1. `productPreview`
2. `hero`
3. `sprintPath`
4. `execLoop`
5. `starterSystem`
6. `durability`
7. `socialProof`
8. `faq`
9. `pricing`
10. `footer`

Two anchors are part of the public contract:

- `id="system"` from the sprint-path section
- `id="pricing"` from the pricing section

Do not rename or remove those casually. Browser smoke checks them today.

## CTA target contract

Hero and pricing do not own checkout behavior directly anymore.

They both consume the shared `HomePageCtaTarget` model from `config/product.ts` and render through `app/_components/home-page/sections/home-page-primary-cta.tsx`.

Current target kinds:

- `checkout`
- `link`

Safe rules:

- if you need a normal link CTA, use `kind: "link"` with `href`
- if you need checkout, use `kind: "checkout"`
- do not import `CheckoutButton` straight into hero or pricing again
- if you add a new CTA target kind, update the target union, the render model, the CTA renderer, and the tests together

## Social proof contract

The public conceptual section name is now `socialProof`.

The default subtype is still founder-led proof. That means the default page can keep Parker-specific proof while the code speaks in reusable section language.

Important rule:

- GitHub activity fetches must remain conditional through the render model

Today that seam is `socialProof.githubActivityUsername`. If the section is off, the fetch should not run.

## Structured data contract

Homepage schema must match what a visitor can actually see.

Current rules:

- `Organization` always stays
- `FAQPage` only appears when the FAQ section is visible
- `Product` only appears when the pricing section is visible and its CTA target still uses checkout

If you change visible sections or pricing intent, update `app/_lib/home-page-structured-data.ts` and the matching tests in the same slice.

Truthful omission is the rule. If a section is gone, its schema should be gone too.

## Safe change patterns

### Change copy only

Edit:

- `app/_content/home-page.ts`
- `public/` if assets change

Usually you should not need to touch the render model for pure copy work.

### Change Blueprint demo copy or fields

Edit:

- `app/_content/home-page.ts`
- `tests/unit/home-page-content.test.ts`
- `tests/integration-ui/home-page-product-preview.test.tsx`

The first-screen `productPreview` section now opens with the dark leverage hero
from the Figma landing-page selection, then continues into the interactive
Blueprint demo that mirrors the real `/blueprint` workspace. The product-preview
CTA is a real checkout action: clicking "Generate my codebase" persists the
latest demo draft to `localStorage` (key `sbs:home-blueprint-draft:v1`) before
starting Stripe checkout, and a workspace-mounted seeder hydrates that draft into
Convex on the first authenticated `/blueprint` load when the buyer has no saved
facts.

Hard rules when editing this section:

- Always show all 7 canonical Blueprint sections (`foundation`, `problem`,
  `outcome`, `design`, `pricing`, `setup`, `generated-preview`) in canonical
  order. Foundation, Design, and Pricing are interactive; the other four are
  visible-but-locked rows. Do not renumber.
- Keep the leverage hero copy in `productPreviewSection.leverageHero` and the
  rendering in `blueprint-demo-leverage-hero.tsx`. Do not reintroduce the old
  "Spec your product" intro, Blueprint explainer paragraph, or checkout unlock
  note above the demo.
- Source field labels and helper text from `@shipbysunday/blueprint-presentation`.
  Source design preset definitions and the canonical
  `buildDesignPresetFactSeed(presetId)` from `@shipbysunday/blueprint-compiler`.
  Do not edit `theme_preset` directly on the homepage; only set it via
  `buildDesignPresetFactSeed(presetId).theme_preset`.
- The bottom CTA must persist the latest draft via the shared
  `onBeforeCheckout` callback on `HomePagePrimaryCta`/`CheckoutButton` before
  the redirect runs. Do not import `CheckoutButton` directly into the demo and
  do not bypass the callback.

### Change Blueprint demo persistence or seeder behavior

Edit:

- `app/_components/home-page/sections/blueprint-demo/home-page-blueprint-draft-storage.ts`
- `app/_components/home-page/sections/blueprint-demo/use-home-page-blueprint-draft.ts`
- `app/checkout/_hooks/use-stripe-checkout.ts`
- `app/checkout/_components/checkout-button.tsx`
- `app/_components/home-page/sections/home-page-primary-cta.tsx`
- `lib/blueprint-flow/use-blueprint-local-draft-seeder.ts`
- `app/(workspace)/_components/blueprint-flow/blueprint-local-draft-seeder.tsx`
- `tests/unit/home-page-blueprint-draft-storage.test.ts`
- `tests/integration-ui/blueprint-local-draft-seeder.test.tsx`
- `tests/integration-ui/checkout-button.test.tsx`

Hard rules:

- `localStorage` envelope is versioned: `{ version: 1, savedAt, fields }`.
  Reject wrong versions, corrupt JSON, unknown keys, and non-finite or
  negative pricing strings. The single key is `sbs:home-blueprint-draft:v1`.
- The seeder must run client-side under the workspace blueprint flow, wait
  for authenticated `workspaceState`, and only call
  `saveProjectDefinitionFacts` when the workspace facts are empty
  (`Object.keys(workspaceState.projectDefinition?.facts ?? {}).length === 0`).
- Clear `localStorage` on a successful seed or when facts already exist (so an
  old marketing draft cannot overwrite a returning buyer). Preserve the key on
  mutation failure so a future render can retry.
- Convex remains the source of truth after seeding. The seeder is a one-time
  import bridge, not a second persistent draft source.

### Turn a section on or off

Edit:

- `config/product.ts`
- `app/_lib/home-page-render-model.ts` only if the section has data-fetch side effects
- `app/_lib/home-page-structured-data.ts` if the section affects schema
- tests if default public behavior changes

### Change hero or pricing CTA behavior

Edit:

- `config/product.ts`
- `app/_lib/home-page-render-model.ts`
- `app/_components/home-page/sections/home-page-primary-cta.tsx` only if the target model changes
- `app/_lib/home-page-structured-data.ts` if pricing is no longer a checkout path

### Add or remove a top-level section

Edit all of these together:

- `config/product.ts`
- `app/_content/home-page.ts`
- `app/_lib/home-page-render-model.ts`
- `app/_components/home-page/home-page.tsx`
- `app/_lib/home-page-structured-data.ts`
- smoke tests and unit tests
- this doc

If you do not update all of those in one slice, the homepage contract will drift.

## What a future AI agent should preserve

If you ask an agent to change the homepage, the prompt should say which of these is changing:

- config
- content
- behavior
- schema
- tests

The agent should preserve these invariants unless the task explicitly changes them:

- fixed section order
- product-preview first screen when enabled
- truthful schema
- conditional social-proof fetch behavior
- shared CTA renderer
- `system` and `pricing` anchors in the default path

## What success looks like

You changed the homepage correctly when:

- the visible page matches the starter config
- the CTA path is explicit
- the schema matches the visible sections
- the tests still prove the public contract
- the next agent can understand the seam by reading this page plus the files listed above
