# Deploy to Vercel

Production is mostly an env-parity problem.

## Before the first deploy

Prepare production values in your hosting dashboards and provider dashboards. Mirror the same categories you use locally and verify they match across systems:

- Clerk publishable and secret keys
- Clerk frontend API URL
- Convex client URL (`NEXT_PUBLIC_CONVEX_URL`)
- Convex HTTP-actions URL (`NEXT_PUBLIC_CONVEX_SITE_URL`) when the deployment uses Convex HTTP actions
- Stripe secret key, product id, and price id
- live `STRIPE_WEBHOOK_SECRET`
- `APP_BASE_URL`

## Vercel checklist

- deploy as a normal Next.js app
- keep the project linked to `ParkerRex/mma-shipbysunday`
- keep Vercel's production branch on `main`
- keep Bun pinned to the repo version
- use real production Clerk env values
- use real production Stripe live keys
- set `NEXT_PUBLIC_CONVEX_SITE_URL` when the deployment uses Convex HTTP actions

Do not make Vercel responsible for production Convex deploys in this repo. The frontend should build on Vercel, but Convex production promotion still happens from GitHub Actions through `.github/workflows/convex-production-deploy.yml`.

## Post-deploy verification

After a release merge to `main`, the deployed proof is the deployment smoke workflow, not a separate QA pack.

The live path is:

1. Vercel deploys the merged `main` commit.
2. GitHub receives the successful `deployment_status`.
3. `.github/workflows/deployment-smoke.yml` runs against the exact deployed URL.
4. That smoke suite verifies the public pages and, when `PLAYWRIGHT_CHECKOUT_SMOKE=1`, the real checkout-session creation route.

If the deployed checkout smoke fails, debug environment drift first. The goal is to fail at the real deployed boundary, not to recover that information through a second orchestration layer.
