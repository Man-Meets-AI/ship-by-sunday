# Deploy to Vercel

Production is mostly an env-parity problem.

The most common mistake is getting Vercel, Clerk, Convex, and Stripe individually “working” while the cross-system values still drift.

## Before the first deploy

Prepare production values in your hosting dashboards and provider dashboards. Mirror the same categories you use locally and verify they match across systems:

- Clerk publishable and secret keys
- Clerk frontend API URL
- Convex client URL (`NEXT_PUBLIC_CONVEX_URL`)
- Convex HTTP-actions URL (`NEXT_PUBLIC_CONVEX_SITE_URL`) when the deployment uses Convex HTTP actions
- any deployment values your Convex environment writes
- Stripe secret key, product id, price id
- live `STRIPE_WEBHOOK_SECRET`
- `APP_BASE_URL`
- PostHog source-map upload values when error tracking is enabled:
  `NEXT_PUBLIC_POSTHOG_TOKEN`, `NEXT_PUBLIC_POSTHOG_HOST`,
  `POSTHOG_PROJECT_ID`, and `POSTHOG_API_KEY`

The observability-specific signing secrets, ingest token, incident-control token, and Telegram alerting values are documented in the internal observability runbook.

## Vercel checklist

- deploy as a normal Next.js app
- keep the Vercel project linked to the intended GitHub repository before reconnecting it
- grant the Vercel GitHub App access to the intended GitHub repository before reconnecting the project if the repository is private
- keep Vercel's production branch on `main`
- let Preview continue to handle feature branches
- keep Bun pinned to the repo version
- use real production Clerk env values
- use real production Stripe live keys
- if the app uses observability or any other Convex HTTP actions, set `NEXT_PUBLIC_CONVEX_SITE_URL` to the matching `.convex.site` host
- if the app uploads PostHog source maps, set `POSTHOG_PROJECT_ID` and `POSTHOG_API_KEY` in Vercel; the API key must be a project-scoped PostHog personal API key with only the `Source map upload` scope
- keep PostHog MCP credentials out of Vercel app env; MCP uses operator OAuth or a separate `MCP Server` key outside runtime config

Do not make Vercel responsible for production Convex deploys in this repo. The frontend should build on Vercel, but Convex production promotion now happens from GitHub Actions on `main` through `.github/workflows/convex-production-deploy.yml`.

`CONVEX_DEPLOY_KEY` belongs in GitHub repository secrets for that workflow, not in the Vercel project.

## Convex checklist

Convex production must match the same production auth and Stripe values used by the app.

Do not leave Convex pointed at:

- an old Clerk instance
- a dev Clerk instance
- an outdated Stripe webhook secret
- a mismatched Stripe secret key
- a deployment that does not have the current `observability` functions pushed

## Post-deploy verification

After a merge to `main`, `Production Release Proof` should confirm all of this with a real test flow. That workflow should wait for the exact Vercel production deployment for the merged commit before it starts browser verification, not just wait for the production URL to return `200`.

1. signed-out visitor hits a protected route and is pushed to sign-in
2. signed-in user without access reaches a protected workspace route and sees inline recovery
3. live checkout returns to `/checkout/success`
4. webhook grants access
5. newly granted user reaches `/workspace/choose`
6. Vercel attributes the production web deploy to `main`
7. GitHub Actions reports a matching `Convex Production Deploy` run for the same release

The workflow should use the same release proof command for the authenticated production pass:

```bash
PLAYWRIGHT_BASE_URL=https://<production-url> QA_ENV_FILE=apps/web/.env.production bun run release:proof -- --proof=default_ship
```

That command assumes:

- `tmp/release-personas.local.json` contains the real release proof account emails, unless `RELEASE_PERSONAS_LOCAL_FILE` points somewhere else
- the file referenced by `QA_ENV_FILE` contains the production Clerk and Convex env values
- the production Clerk instance matches the target site
- the production Clerk instance allows the release proof accounts to receive an email-code challenge; the browser proof sends the code before using Clerk testing sign-in tokens for deterministic storage state
- GitHub repository secret `VERCEL_TOKEN` plus repository variables `VERCEL_PROJECT_ID` and `VERCEL_TEAM_ID` can read production deployment metadata so the workflow can wait for the exact release commit before running Playwright
- `QA_ENV_FILE=apps/web/.env.production` is resolved from the repository root in CI, not from `apps/web/`
- the production proof bootstrap can derive `CONVEX_DEPLOYMENT` from `NEXT_PUBLIC_CONVEX_URL`, so the env file does not need a separate production deployment name

If persona prep fails with a Clerk publishable-key mismatch, stop there. That means the loaded env file does not match the production site, so any later authenticated browser result would be invalid.

For billing-sensitive releases, the same workflow should also run:

```bash
PLAYWRIGHT_BASE_URL=https://<production-url> QA_ENV_FILE=apps/web/.env.production bun run release:proof -- --proof=billing_integration
```

Only billing-sensitive releases should spend that extra live no-cost Checkout proof.

When PostHog error tracking is enabled, the production build uses `@posthog/nextjs-config` to upload source maps. After the build, run:

```bash
bun run posthog:proof
```

That command verifies PostHog env presence and injected source-map chunk IDs without printing secret values. Source maps may be deleted locally after a successful upload. The final manual check is in PostHog: confirm the production symbol set uploaded and a sampled issue resolves to readable application frames.

## What success looks like

Production is healthy when payment, access, route protection, observability, and deployment provenance all agree on the same release. In this repo that means the web app came from Vercel `main`, the backend came from the Convex production workflow on `main`, and both use the same production env values.

If payment completes but access does not, debug env parity before you rewrite application code.
