# Telegram Support Bot

The homepage support widget is first-party UI. Visitors stay on the landing page, and Parker replies from a support-configured Telegram bot in a forum-topic support group.

The browser never receives a support bearer token. The widget talks to `/api/support/messages`, and the Next.js route stores the support session in an HttpOnly, Secure `__Host-sbs_support_session` cookie.

## Create the Telegram side

1. In `@BotFather`, create a dedicated support bot or deliberately reuse an existing bot that is already allowed to create forum topics. Store the token as `TELEGRAM_SUPPORT_BOT_TOKEN` in Convex.
2. In `@BotFather`, disable privacy mode for this bot so normal operator replies in the support group are delivered as `message` updates. Verify with `getMe`; `can_read_all_group_messages` should be `true`.
3. Create a dedicated Telegram supergroup for support and enable Topics.
4. Add the support bot to the group as an administrator.
5. Grant these bot rights:
   - `can_manage_topics`: required for `createForumTopic` and for closing or reopening topics.
   - `can_delete_messages`: required for `deleteForumTopic` when retention cleanup starts deleting closed support topics.
6. Find the support group chat id and store it as `TELEGRAM_SUPPORT_CHAT_ID` in Convex. Supergroup ids usually look like `-100...`.
7. Find each allowed operator's Telegram user id and store a comma-separated list as `TELEGRAM_SUPPORT_OPERATOR_USER_IDS` in Convex.

Hosted smoke and production setups can share the same support bot/group when webhook delivery points at the active Convex site URL: `https://<your-convex-site>.convex.site/telegram/support/webhook`. The bot must be an administrator with `can_manage_topics` and `can_delete_messages`. Reusing any existing bot is only safe when nothing else depends on long polling for that bot, because Telegram allows either a webhook or `getUpdates` polling, not both. Rotate any bot token that was pasted into chat or a terminal transcript before treating the setup as production-safe.

## Configure Convex env

Set these on the hosted Convex deployment that owns the web app data:

```bash
bunx convex env set TELEGRAM_SUPPORT_BOT_TOKEN "<bot-token>"
bunx convex env set TELEGRAM_SUPPORT_CHAT_ID "<support-group-id>"
bunx convex env set TELEGRAM_SUPPORT_OPERATOR_USER_IDS "<telegram-user-id>,<telegram-user-id>"
bunx convex env set TELEGRAM_SUPPORT_WEBHOOK_SECRET "<secret-token>"
bunx convex env set TELEGRAM_SUPPORT_ADMIN_RECOVERY_TOKEN "<random-recovery-token>"
bunx convex env set OPENAI_API_KEY "<openai-api-key>"
```

Before registering the webhook, run a presence-only readiness probe from `apps/web`.
Do not print raw values:

```bash
for name in TELEGRAM_SUPPORT_BOT_TOKEN TELEGRAM_SUPPORT_CHAT_ID TELEGRAM_SUPPORT_OPERATOR_USER_IDS TELEGRAM_SUPPORT_WEBHOOK_SECRET TELEGRAM_SUPPORT_ADMIN_RECOVERY_TOKEN OPENAI_API_KEY; do
  value="$(bunx convex env get "$name" 2>/dev/null)"
  if [ -n "$value" ]; then
    printf "%s present\n" "$name"
  else
    printf "%s missing_or_empty\n" "$name"
  fi
done
```

Every Telegram support name must print `present` before Telegram proof can run. `OPENAI_API_KEY` must print `present` before live OpenAI draft proof can run; if it is missing, AI-backed buttons should use the deterministic private fallback path.

`TELEGRAM_SUPPORT_WEBHOOK_SECRET` must be the same value sent to Telegram as `setWebhook.secret_token`. Telegram will echo it back in the `X-Telegram-Bot-Api-Secret-Token` header. Telegram requires this token to be 1-256 characters and only `A-Z`, `a-z`, `0-9`, `_`, and `-`.

Optional kill switch:

```bash
bunx convex env set SUPPORT_CHAT_DISABLED "1"
```

Unset `SUPPORT_CHAT_DISABLED` or set it to `0` to re-enable the widget bridge.

Optional AI model override:

```bash
bunx convex env set SUPPORT_AI_DRAFT_MODEL "gpt-5.4-mini-2026-03-17"
```

If `SUPPORT_AI_DRAFT_MODEL` is unset, support drafts use `gpt-5.4-mini-2026-03-17`.

## Register the webhook

Use the Convex site URL, not the browser client URL:

```bash
curl -X POST "https://api.telegram.org/bot$TELEGRAM_SUPPORT_BOT_TOKEN/setWebhook" \
  -H "Content-Type: application/json" \
  -d '{
    "url": "https://<your-convex-site>.convex.site/telegram/support/webhook",
    "secret_token": "'"$TELEGRAM_SUPPORT_WEBHOOK_SECRET"'",
    "allowed_updates": ["message", "callback_query"],
    "drop_pending_updates": false
  }'
```

Keep `allowed_updates` narrow. This bridge only accepts `message` replies and `callback_query` actions from the support topic inline keyboard.

## Visitor acknowledgement

On the first visitor message in a support thread, the website stores the visitor message and then shows two system acknowledgement messages:

```text
Got it. This went straight to Parker's Telegram.

He'll reply here when he can.
```

These are `system` messages in Convex. They appear in the website widget only and are not sent to Telegram as visitor messages. They intentionally do not claim Parker is online and do not promise a response time.

## Screenshots and bug reports

The support widget accepts one explicit customer-selected screenshot per message. Supported screenshot formats are PNG, JPG, and WebP up to 10 MB. The browser asks `/api/support/attachments` for a Convex storage upload URL using the existing HttpOnly support session cookie, uploads the file directly to Convex storage, and then sends the resulting storage id through `/api/support/messages`. The browser never receives a support bearer token or Telegram bot token.

When a message includes a screenshot, Convex validates the stored blob metadata again before the visitor message is created. Telegram receives the text message in the customer topic and then receives the screenshot through `sendPhoto` with a short caption. The website transcript shows the screenshot inside the same visitor bubble when Convex can return a signed storage URL.

The widget also has a `Bug` mode. That mode sends a structured visitor message with impact, page path, viewport, browser user agent, what happened, what the customer was doing, and what they expected instead. The app does not automatically attach workspace source, logs, local paths, payment details, or transcript DOM. Customers must explicitly type the bug report and explicitly choose any screenshot.

Screenshot storage follows the same closed-thread retention path as support transcripts. When closed transcripts are purged, message bodies are removed and attached screenshot files are deleted from Convex storage before Telegram topic cleanup is attempted.

## Operator action buttons

Every support topic starts with a bot-authored header and an inline keyboard. Normal Telegram replies from allowlisted operators still become website-visible replies.

New support topics show this default keyboard:

```text
Yoooo | Whatcha
Draft Parker
Close
```

These buttons send website-visible operator messages after an allowlisted operator taps them:

- `Yoooo`: sends `Yooo - how'd you find my site?`
- `Whatcha`: sends `Whatcha trying to make?`

`Draft Parker` is operator-only and AI-backed when `OPENAI_API_KEY` is configured. It posts a private Parker-style draft in the Telegram topic only. The generated Telegram note includes `Send draft` and `Discard` buttons. `Send draft` writes the generated draft to the visitor transcript as one normal operator message. `Discard` prevents that generated draft from being sent later. Duplicate `Send draft` or `Discard` callbacks do not create duplicate visitor-visible messages.

`Close` closes the website thread and starts the closed-transcript retention window.

Older in-flight Telegram keyboards may still include legacy buttons. The webhook continues to validate those callback payloads safely, but new topic headers do not show them by default.

These buttons are operator-only and AI-backed when `OPENAI_API_KEY` is configured:

- `Summary`: posts a private AI lead summary in the Telegram topic only
- `Codex prompt`: posts a private paste-ready Codex prompt in the Telegram topic only
- `Linear draft`: posts a private paste-ready Linear issue draft in the Telegram topic only

Legacy AI and Linear buttons are draft-only unless the explicit `Send draft` decision is present for a `Draft Parker` reply. They do not create a Linear issue and do not send generated text to the visitor automatically. Each button creates a `supportOperatorActions` audit record with the operator id, callback query id, source message when available, AI generation status, generated output when applicable, generated output source, model, generation failure reason, operator-note delivery status, Telegram note message id or delivery failure reason, customer-visible message id when one is created, and draft-send or discard decision when applicable.

When Parker taps an AI-backed button, the callback mutation stores a deterministic private fallback and schedules OpenAI Responses API generation in the same Convex transaction, then the webhook answers Telegram with `answerCallbackQuery`. The Responses request sets `store: false`. If generation succeeds, Convex patches the same audit record with `generatedOutputSource: "openai_responses"` and posts the generated text as a private Telegram topic note. If `OPENAI_API_KEY` is missing or OpenAI fails, Convex keeps `generatedOutputSource: "deterministic"`, records `generationFailureReason`, and posts the deterministic fallback note instead. If Telegram cannot receive that private note, Convex records `operatorNoteDeliveryStatus: "delivery_failed"` and leaves the AI generation result intact.

AI output is not inserted into `supportMessages` or shown in the homepage widget transcript until Parker explicitly taps `Send draft` or sends a normal Telegram reply manually. Generated output must not be sent to PostHog.

Telegram inline keyboard callback data is limited to 1-64 bytes, so the app uses compact `support:<support-id>:<action>` callback data for topic actions and `draft:<operator-action-id>:<decision>` for draft decisions. The webhook answers callback queries with `answerCallbackQuery` so Telegram clients do not leave a spinner running.

## Verify setup

Run:

```bash
curl "https://api.telegram.org/bot$TELEGRAM_SUPPORT_BOT_TOKEN/getWebhookInfo"
```

Check that:

- `url` is `https://<your-convex-site>.convex.site/telegram/support/webhook`
- `allowed_updates` is exactly `["message", "callback_query"]`
- `pending_update_count` is not growing after test messages
- `last_error_message` is absent

Then open the homepage, open the Message Parker launcher, and send a test message. A new Telegram topic named with the `SBS-...` support id and safe entry label should appear, such as `homepage` or `workspace`. Reply in that topic from an operator user listed in `TELEGRAM_SUPPORT_OPERATOR_USER_IDS`; the reply should appear in the widget on the next refresh or poll. Signed-in buyers also get an `Ask Parker` launcher inside protected workspace routes; messages from that launcher use the same support thread bridge with `entrySurface: "workspace_support_widget"` and do not send workspace source, findings, logs, local paths, or payment details automatically.

Click `Yoooo` in Telegram. The widget should show `Yooo - how'd you find my site?` after refresh. Click `Whatcha`; the widget should show `Whatcha trying to make?` after refresh. Click `Draft Parker`; Telegram should first acknowledge the button tap, then receive an operator-only AI note with `Send draft` and `Discard`. The widget should not receive a new message from the AI action until `Send draft` is tapped. Click `Close`; the widget should show the closed state after refresh.

To verify screenshot and bug-report handling, open the widget, switch to `Bug`, fill the bug fields, attach a small PNG screenshot, and send. The website should render the visitor bubble immediately with a sending state, then show the uploaded screenshot after the Convex response returns. The Telegram topic should receive the structured bug text and a separate photo message. The structured text should include page, viewport, and browser context only; it should not contain source code, logs, local filesystem paths, payment details, or workspace transcript DOM.

To verify the AI provider path, set `OPENAI_API_KEY`, tap `Draft Parker`, and inspect the `supportOperatorActions` record for that callback. It should keep the same action row, set `aiDraftGenerationStatus` to `completed`, set `generatedOutputSource` to `openai_responses`, set `generatedOutputModel` to the active support draft model, record `operatorNoteDeliveryStatus`, and leave `supportMessages` unchanged until `Send draft` is tapped. Tap `Send draft` and verify exactly one operator support message is created. Tap `Send draft` again and verify no duplicate message is created. Unset `OPENAI_API_KEY` only in a non-production deployment and tap a new AI button to prove the fallback path: Telegram should receive the deterministic fallback note and the action row should contain `generationFailureReason`.

## Operations runbook

Convex runs `support retention maintenance` every six hours from `apps/web/convex/crons.ts` on the hosted deployment. It closes idle anonymous open threads after 14 days, retains closed transcript bodies for 90 days, purges `supportMessages.body` and `supportOperatorActions.generatedOutput` after the retention window, and then attempts Telegram `deleteForumTopic` when the thread has a known Telegram topic id. Failed Telegram topic cleanup is selected again on later maintenance runs, so fixing bot permissions or transient provider failures lets the next run delete the already-purged topic. The support audit rows remain; purge removes transcript content and generated operator output, not the fact that the thread or action existed.

Signed-in workspace support threads are not auto-closed by this retention worker. Their `idleCloseAfter` timestamp is moved forward so they stay visible until a later account-history plan defines a signed-in retention policy.

Use the token-protected operations snapshot before a recovery session:

```bash
bunx convex run supportAdmin:getOperationsSnapshot '{"recoveryToken":"<random-recovery-token>"}'
```

The snapshot returns bounded metadata only: failed visitor message ids, support ids, failure classes, delivery attempt counts, operator-note delivery failures, idle threads due for close, transcripts due for purge, and Telegram topic cleanup failures. It does not return support message bodies, emails, Telegram user ids, visitor session tokens, or AI-generated output.

Manual visitor-message retry remains explicit:

```bash
bunx convex run supportAdmin:retryFailedVisitorMessage '{"messageId":"<supportMessages-id>","recoveryToken":"<random-recovery-token>"}'
```

Retry is allowed only when the message is visitor-authored, still has an unpurged body, belongs to an open unpurged thread, has `deliveryStatus: "delivery_failed"`, has a retryable failure class, and has fewer than five recorded delivery attempts. Convex claims the message by moving it back to `sending` before calling Telegram, so repeated retry commands for the same message are rejected while one delivery attempt is in flight. `content_rejected` messages, closed threads, purged messages, in-flight messages, and over-attempted messages are not retried. Fix the provider setup first, then retry once and inspect the returned thread state.

Support PostHog events are metadata-only. They may include support surface, entry surface, page path, thread status, message count, latest delivery status, delivery failure class, and generic failure class. They must not include message text, email addresses, Telegram ids, raw support session tokens, transcript DOM, or generated AI output. The transcript log keeps `data-ph-no-capture="true"` plus `ph-no-capture ph-sensitive`, and the textarea keeps `data-ph-mask="true"` plus `ph-mask ph-sensitive`.

## Failure shapes

- Missing or wrong `X-Telegram-Bot-Api-Secret-Token`: Convex returns `401`, and Telegram will retry.
- Invalid JSON: Convex returns `400`, and Telegram will retry.
- Missing support chat id or operator allowlist after a valid webhook secret: Convex returns `200` with an ignored setup reason so Telegram does not retry a non-actionable update.
- Unsupported update shape, unknown chat, unknown operator, missing topic, command, or media-only message: Convex returns `200` with an ignored reason so Telegram does not retry noise.
- Missing `OPENAI_API_KEY` or OpenAI provider failure: the webhook still returns `200`, the AI action keeps deterministic private output, `generationFailureReason` is recorded, and no website-visible message is created.
- Thread closed or purged before a scheduled AI draft runs: Convex marks the action's AI draft generation as failed, records the context-unavailable reason, marks the private operator note as delivery failed, and creates no website-visible message.
- Private Telegram note delivery failure: the webhook still returns `200`, the action row records `operatorNoteDeliveryStatus: "delivery_failed"` with the failure reason, and no generated output is inserted into `supportMessages`.
- Retention cleanup failure: the thread records `telegramTopicCleanupStatus: "failed"` with `telegramTopicCleanupFailureReason`; transcript bodies remain purged, and later maintenance runs retry Telegram topic deletion after bot permissions or provider errors are repaired.
- `Forbidden: not enough rights` from Telegram delivery usually means the bot is missing `can_manage_topics` or was not added as an administrator.
- Closed-topic cleanup failures usually mean the bot is missing `can_delete_messages`.

Telegram API references: [setWebhook](https://core.telegram.org/bots/api#setwebhook), [getWebhookInfo](https://core.telegram.org/bots/api#getwebhookinfo), [createForumTopic](https://core.telegram.org/bots/api#createforumtopic), [deleteForumTopic](https://core.telegram.org/bots/api#deleteforumtopic), [InlineKeyboardButton](https://core.telegram.org/bots/api#inlinekeyboardbutton), and [answerCallbackQuery](https://core.telegram.org/bots/api#answercallbackquery).
