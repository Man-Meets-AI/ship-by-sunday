# Stripe Checkout + Webhook

The Stripe setup has one job: turn a real paid checkout into a real product-access grant.

The easiest way to break that path is endpoint drift in Stripe or secret drift between the app and Convex.

In local development, this repo also treats the Stripe CLI project name as a guardrail. The pinned local profile is `ship-by-sunday`, but the runtime source of truth is still `STRIPE_SECRET_KEY` from `apps/web/.env.local`.

For production in this repo, the live Stripe webhook should target the app origin:

`https://<your-app-domain>/api/stripe/webhook`

If Stripe is still pointed at `https://<your-convex-production-deployment>.convex.site/stripe/webhook`, Checkout may still hit the legacy compatibility path instead of the migrated billing-domain sync path.

For incident-control, webhook-alert, and Telegram-delivery drills, use the internal observability runbook instead of rebuilding that flow from this page.

## Required Stripe env values

Add these to `.env.local`:

```bash
STRIPE_SECRET_KEY=
STRIPE_PUBLISHABLE_KEY=
STRIPE_STARTER_PRODUCT_ID=
STRIPE_STARTER_PRICE_ID=
STRIPE_WORKERS_PRODUCT_ID=
STRIPE_WORKERS_PRICE_ID=
STRIPE_WEBHOOK_SECRET=
CONVEX_WEBHOOK_MUTATION_SECRET=
CHECKOUT_FULFILLMENT_RETRY_SECRET=
APP_BASE_URL=
NEXT_PUBLIC_CONVEX_SITE_URL=
CLERK_SECRET_KEY=
```

`STRIPE_PUBLISHABLE_KEY` is safe to expose to the browser. The app returns it from the Express Checkout session route so homepage Link, Apple Pay, and Google Pay buttons can initialize Stripe.js without exposing any secret key.

## Create the product and price

If you do not already have them, create the Starter and Workers products and default prices from the repo:

```bash
bun run stripe:create-product
```

The script prints `STRIPE_STARTER_PRODUCT_ID`, `STRIPE_STARTER_PRICE_ID`, `STRIPE_WORKERS_PRODUCT_ID`, and `STRIPE_WORKERS_PRICE_ID`. Put the test-mode values in `.env.local` and the live-mode values in production Vercel env. Hosted preview and production billing proof require both managed prices. Starter must be a one-time price; Workers must be a recurring subscription price. Local checkout can run without them because the app falls back to inline price data for whichever offer is missing a managed price ID.

## Start dev webhook forwarding

Use this command for local buyer-flow QA against your hosted Convex dev deployment:

```bash
bun run stripe:listen:dev
```

If you want one command that starts the web app, hosted Convex dev sync, and Stripe forwarding together, use:

```bash
bun run dev
```

`bun run dev:full` remains as a compatibility alias for the same full stack.

That helper:

- starts Stripe CLI forwarding to `{APP_BASE_URL}/api/stripe/webhook`, defaulting to `http://localhost:3000/api/stripe/webhook`
- checks the pinned Stripe CLI project `ship-by-sunday` and warns with `stripe login --project-name ship-by-sunday` if the CLI context drifted
- captures the current webhook signing secret
- writes that secret into `.env.local`
- syncs `CONVEX_WEBHOOK_MUTATION_SECRET`, `CHECKOUT_FULFILLMENT_RETRY_SECRET`, `STRIPE_SECRET_KEY`, and `CLERK_SECRET_KEY` into the active hosted Convex dev env

The app also uses `CONVEX_WEBHOOK_MUTATION_SECRET` as the server-only token that lets trusted Next.js routes write billing sync state into Convex. `CHECKOUT_FULFILLMENT_RETRY_SECRET` remains the separate token used when checkout API routes write Convex purchase intents and when `/checkout/success` asks Convex to retry paid-session fulfillment. Set both values in `.env.local`, Vercel, and the active Convex deployment. Do not expose either value to the browser. Missing or mismatched `STRIPE_WEBHOOK_SECRET` makes the app route fail Stripe signature verification. Missing or mismatched `CONVEX_WEBHOOK_MUTATION_SECRET` makes verified webhooks fail before billing state is written. Missing or mismatched retry-secret values make checkout fail before Stripe handoff or make the success-page retry return an invalid checkout session.

It also expects `.env.local` to contain the `CONVEX_DEPLOYMENT` value that `bun run dev:convex` writes.
In this repo, that same `bun run dev:convex` sync also needs to leave `NEXT_PUBLIC_CONVEX_SITE_URL` in `.env.local`, because the Next.js route writes into hosted Convex after Stripe signature verification.

If the listener writes a fresh secret while the app is already running, restart the app before testing checkout.

Subscribe the Stripe webhook endpoint only to `checkout.session.completed`, `checkout.session.async_payment_succeeded`, `customer.subscription.created`, `customer.subscription.updated`, `customer.subscription.deleted`, `invoice.payment_failed`, and `invoice.paid`. Do not use wildcard event subscriptions. The endpoint URL must be exactly `{APP_BASE_URL}/api/stripe/webhook`; do not add a trailing slash. Use webhook endpoint API version `2023-08-16` or later, or leave the endpoint on an account default that is at least that new, so no-cost Checkout events render correctly. The app webhook accepts an unpaid `checkout.session.completed` event without granting access, then waits for the later async success event before fulfilling delayed-payment checkouts.

Before production billing proof, `bun run release:billing:doctor -- --env=production` verifies that the configured Stripe mode, Starter price, Workers price, app checkout route, Stripe Dashboard webhook endpoint, and `CONVEX_WEBHOOK_MUTATION_SECRET` boundary all match this contract. Stripe only returns a webhook endpoint signing secret when the endpoint is created, so the doctor verifies that `STRIPE_WEBHOOK_SECRET` is present and shaped like a Stripe signing secret; it cannot compare the saved secret back to Stripe.

## Use test mode first

Do not start by wiring live mode.

Start in a safe sandbox or test-mode environment, get the full handoff working there, and only then mirror the same setup into production.

## The handoff architecture

The starter and worker offers use this sequence:

1. buyer calls `POST /api/stripe/checkout` from `/starter` or `/workers`, whether they are signed in or signed out
2. eligible homepage visitors can instead initialize `POST /api/stripe/checkout/express` and pay through Stripe's Express Checkout Element
3. Stripe hosts checkout or confirms the Express Checkout Session
4. Stripe returns to `/checkout/success`
5. Stripe webhook hits the Next.js app route at `{APP_BASE_URL}/api/stripe/webhook`
6. the app route verifies the signature, resolves the current Stripe state, and writes billing state into Convex through the secret-gated sync boundary
7. `/checkout/success` retries the same paid-session fulfillment if the webhook is delayed, then sends signed-out buyers to `/sign-in` with an offer-specific redirect
8. after Clerk verifies the checkout email with email-code OTP, Starter buyers land on `/starter/home` and Workers buyers land on `/workers/setup`

New Checkout Sessions write the compact `mma_checkout_v1` metadata packet to both Checkout Session metadata and PaymentIntent metadata. The packet carries `app`, `accessProduct`, `checkoutSurface`, `purchaseIntentId`, `offerId`, and the optional `clerkUserId`; do not add `courseSlug`, `buyerStartingPoint`, `checkoutCtaId`, or pre-purchase path intent to new public checkout metadata. Pending checkout claims and legacy checkout intent fields still exist as fallback and audit records. They are not the happy-path customer journey. Checkout purchase intent writes are protected by the server-only fulfillment retry secret and are reconciled when product access is granted from either the webhook worker or the checkout-success recovery path.

## Express Checkout setup

Express Checkout is progressive enhancement. The hosted Checkout button remains visible when no wallet method is available, when Stripe.js fails to initialize, or when provider setup is incomplete.

To make the direct homepage payment button appear:

- Enable Link and the wallet payment methods you want in the Stripe Dashboard payment-method settings for both test and live mode.
- Register the homepage domain in Stripe payment method domains for both test and live mode.
- Serve the page over HTTPS outside localhost browser testing.
- Set `STRIPE_PUBLISHABLE_KEY` beside the matching `STRIPE_SECRET_KEY`.
- Keep the webhook endpoint pointed at `{APP_BASE_URL}/api/stripe/webhook`; Express Checkout still fulfills from Checkout Session webhook events.

## Health checks

Use these commands before you debug by hand:

```bash
bun run stripe:dev:doctor
bun run stripe:dev:verify
```

`bun run stripe:dev:doctor` compares the app Stripe account from `apps/web/.env.local` against the pinned Stripe CLI project `ship-by-sunday`. The listener itself still runs from `STRIPE_SECRET_KEY`, so a CLI mismatch is a local guardrail problem, not a second billing authority.

## What success looks like

The happy path is:

1. checkout completes in Stripe
2. Stripe forwards a paid `checkout.session.completed`, or `checkout.session.async_payment_succeeded` for a delayed payment method
3. the webhook grants product access only after Stripe reports the Checkout Session as paid or no-payment-required
4. signed-out buyers sign in through Clerk email code with the Stripe checkout email locked
5. `/checkout/success` stops waiting or redirects immediately
6. Starter buyers reach `/starter/home`; Workers buyers reach `/workers/setup`; legacy broad-access buyers can still use `/home` as a recovery hub

## If this breaks

The most common failures are:

- the pinned Stripe CLI project `ship-by-sunday` is missing or logged into a different Stripe account than `STRIPE_SECRET_KEY`
- `.env.local`, Vercel, and Convex do not match on `CONVEX_WEBHOOK_MUTATION_SECRET`, `CHECKOUT_FULFILLMENT_RETRY_SECRET`, or `STRIPE_SECRET_KEY`
- the Next.js runtime is missing `STRIPE_WEBHOOK_SECRET`, so the app route cannot verify Stripe signatures
- production Convex is missing `STRIPE_SECRET_KEY` or `CLERK_SECRET_KEY`, so compatibility fulfillment cannot construct Stripe or resolve the checkout email in Clerk even after the signature verifies
- you changed the webhook secret but did not restart the app
- Clerk email-code sign-in is disabled or misconfigured, so `/sign-in` cannot send or verify the one-time code for the Stripe checkout email and may show a Clerk `factor_not_found` error
- Clerk/Convex auth is broken, so the buyer cannot be matched to the right access state
- Express Checkout does not render because the visitor's browser has no eligible wallet, the Stripe publishable key is missing, the domain is not registered, or Link/wallet payment methods are disabled in that Stripe mode

If the doctor says the pinned CLI project is missing or mismatched, repair that exact profile with:

```bash
stripe login --project-name ship-by-sunday
```

If you are seeing a paid session without access, start with [Troubleshooting Stripe and Convex](/docs/troubleshooting/stripe-convex).
