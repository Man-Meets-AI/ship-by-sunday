# Lesson 3.3 UX Critique: Install MCPs and Skills

## Outcome Context

### Product goal

`Ship by Sunday` needs to make the first real coding stretch feel controlled. Lesson `3.3` sits between repo orientation in `3.2` and provider wiring in `3.4`, so it has to turn “I found the repo” into “my execution stack is actually ready.”

### Surface goal

Lesson `3.3` should help the student install the core build tools, verify that each one works in their environment, and leave with a reusable setup record they can trust during integration and debugging.

### Business model

This product is selling guided execution, not just lesson content. A tooling lesson that can be marked complete without real proof weakens trust fast because it sits right before auth, database, and payment setup, where shallow setup mistakes become expensive.

### Business metrics that matter here

- `3.2` to `3.3` continuation rate
- `3.3` completion rate
- percentage of `3.4` starts that do not require reopening `3.3`
- support volume around missing MCP setup, missing skills, or “tool not found” issues
- time from `3.3` start to successful first provider-wiring attempt in `3.4`
- drop-off rate between `3.3` and `3.4`

### Assumptions and confidence

- Assumption: the student already has enough repo context from `3.2` to understand why these tools matter, but still needs explicit setup guidance.
- Assumption: the main job of this lesson is verification, not awareness.
- Assumption: most failure risk here comes from false-positive completion rather than from the lesson being too hard.
- Confidence: high on the structural UX issues because they are visible in the lesson contract, objective-task logic, and shared guided-form shell. Medium on frequency in live use because this pass did not include authenticated browser QA.

## Problems I Notice

### 1. The lesson can be completed without any real setup evidence.

`3.3` requires only three toggles: `Figma MCP installed`, `Playwright MCP installed`, and `Convex, Clerk, and Stripe skills available`. Completion logic in `getObjectiveTasks` treats each toggle as done as soon as it is checked. There is no required command, path, version note, verification step, or failure-state capture.

Impact:

- Students can mark the tooling stack complete without installing or validating anything.
- `3.4` inherits hidden setup debt that looks “approved” by the system.
- Support burden shifts downstream into the harder integration lesson.

### 2. The page teaches awareness of tools, not a reliable install sequence.

The workbench prompt says to “lock your tooling stack,” but the actual interaction is just yes/no confirmation plus an optional note. The lesson does not clearly separate install, verify, and record. That is a mismatch for a setup lesson where order matters.

Impact:

- Students can scan the lesson, check the boxes, and move on without doing the work in order.
- The product feels more like a reminder list than guided execution.
- The first Build-tooling checkpoint is weaker than the Build lessons around it.

### 3. The repo-orientation artifact is pinned, but not turned into operational guidance.

`repo_orientation_ready` appears as generic context, yet the lesson never translates it into “open this repo and install tooling for this exact environment now.” The student is shown prior context, but the lesson does not tell them how that context changes the setup task.

Impact:

- `3.2` and `3.3` feel loosely connected instead of sequenced.
- Students may install tools in the abstract rather than against the repo they just mapped.
- The course misses a chance to show that prior artifacts actively shape Build execution.

### 4. The lesson relies on broad external docs instead of giving a crisp local success bar.

The coach resources point to official Figma, Playwright, Convex, Clerk, and Stripe docs, which is directionally right, but the lesson does not tell the student what “done” looks like locally. There is no explicit confirmation like “the tool appears in Codex,” “the skill is visible in your skill list,” or “this command now works.”

Impact:

- Students can open docs without reaching a verified local state.
- The course pushes key setup judgment back onto the learner right before integration work.
- The tooling stack feels less productized than it should.

### 5. The only persistent setup artifact is too vague to help the next lesson.

`tooling_notes` is optional freeform text. It can capture useful caveats, but the artifact does not require the high-value details that `3.4` actually needs, such as install path, provider-skill names, account/tool context, or any known local gotchas.

Impact:

- The artifact can be empty even when local setup was messy.
- Students lose reusable setup memory right before auth/payment wiring.
- Future prompts and debugging loops have to rediscover context they could have saved once here.

### 6. The `3.3 -> 3.4` handoff is too weak for such a high-risk transition.

Lesson `3.4` depends on `tooling_stack_ready`, but `3.3` does not make the student prove they can actually use those tools on the next step. The lesson says “ready for provider wiring” without ensuring the tools are usable for provider wiring.

Impact:

- The unlock feels formal rather than earned.
- Students may hit preventable friction immediately in `3.4`.
- Confidence drops at the exact point the course asks for deeper technical trust.

## Solutions I Recommend

### 1. Replace the three proof-free toggles with install-plus-verify capture.

What to change:

- Keep the three tool categories, but require one verification field per category:
  - how it was installed
  - how the student confirmed it works
  - one local path, command, or visible success signal
- Keep the final notes field optional, but make verification itself required.

Why it solves the user problem:

- The lesson starts measuring real setup, not intent.
- Students leave with evidence they can reuse when something fails later.

How it supports business growth:

- Fewer false completions should reduce `3.4` friction and support noise.
- The product feels more operationally trustworthy.

Trade-offs or risks:

- The lesson becomes slightly heavier.
- The fields need to stay concise so this does not turn into paperwork.

How to validate:

- Review saved `tooling_stack_ready` artifacts for concrete install evidence.
- Compare `3.4` blocker reports before and after the change.

### 2. Reframe the lesson as a sequenced setup run, not a generic guided form.

What to change:

- Organize the surface into three sections:
  - install MCPs
  - verify provider skills
  - record local caveats
- Consider using a more checklist-like or console-checklist treatment instead of the default guided-form layout if that better matches the task.

Why it solves the user problem:

- It gives the student a clear order of operations.
- It reduces the chance that they skim, toggle, and continue.

How it supports business growth:

- Stronger pacing makes the Build stack feel intentionally coached.
- Better setup discipline compounds through the later Build lessons.

Trade-offs or risks:

- More structure can feel stricter.
- The UI has to stay compact enough that setup still feels fast.

How to validate:

- Browser-QA whether first-time students complete the sequence cleanly without confusion.
- Watch whether fewer users reopen the lesson immediately after entering `3.4`.

### 3. Use `3.2` repo context to personalize the tooling setup task.

What to change:

- Add a small bridge card above the form:
  - repo or starter identified
  - startup command from `3.2`
  - first route or surface they mapped
  - short line explaining why these tools matter for that environment
- Tie the setup to the student’s actual repo, not to tooling in general.

Why it solves the user problem:

- It turns the lesson into the next move in the same repo journey.
- Students understand why they are doing this now, not later.

How it supports business growth:

- The Build sequence feels more coherent and premium.
- Stronger continuity should improve confidence entering `3.4`.

Trade-offs or risks:

- The bridge has to stay brief.
- Custom repos need wording that suggests, rather than overclaims, the exact next surface.

How to validate:

- QA whether students can explain how `3.3` connects to their mapped repo after one read.
- Review whether `tooling_notes` align more closely with the actual repo setup.

### 4. Add explicit local success criteria for each tool.

What to change:

- For each MCP or skill group, show one plain-language `done looks like this` line.
- Examples:
  - Figma MCP is visible and callable in Codex
  - Playwright automation can be invoked locally
  - Convex, Clerk, and Stripe skills appear in the available skill list
- Pair each with the official doc link, instead of relying on the link alone.

Why it solves the user problem:

- Students know what to verify locally before moving on.
- The lesson teaches a success bar, not just a reading assignment.

How it supports business growth:

- The tooling lesson becomes more deterministic and less support-heavy.
- That raises trust at a fragile point in the product journey.

Trade-offs or risks:

- Success criteria must match the real product environment.
- If the app environment changes, the lesson needs maintenance.

How to validate:

- Browser-QA the lesson with a fresh local setup and confirm each success state is obvious.
- Track whether students still misinterpret “installed” after the criteria are added.

### 5. Turn `tooling_notes` into a structured handoff artifact for `3.4`.

What to change:

- Capture a few reusable fields instead of one vague textarea:
  - install caveat
  - account/environment note
  - command or menu path to reopen the tool
  - provider-skill state
- Keep one short freeform note only for truly custom issues.

Why it solves the user problem:

- The saved artifact becomes useful in the next lesson instead of decorative.
- Students do not need to reconstruct setup context from memory.

How it supports business growth:

- Better artifacts reduce repeated friction in integration and debugging.
- The course feels more like a working system and less like disconnected pages.

Trade-offs or risks:

- Slightly more field design work now.
- The artifact has to stay lean enough to remain skimmable later.

How to validate:

- Review whether `3.4` can use the saved artifact directly without reopening docs.
- Check whether students add fewer ad hoc setup notes outside the product.

### 6. Make the `3.4` handoff explicit and earned.

What to change:

- Add a final checkpoint card that says what the learner should now be able to do in `3.4`.
- Example:
  - use provider guidance without searching from scratch
  - reach browser QA quickly
  - capture integration caveats as they wire auth and payments
- Gate the completion CTA on those verification fields, not on trust-only toggles.

Why it solves the user problem:

- It makes the unlock feel justified.
- The student leaves knowing why this lesson mattered.

How it supports business growth:

- A stronger `3.3 -> 3.4` bridge should improve continuation and reduce drop-off.
- The system feels more reliable at the moment technical complexity rises.

Trade-offs or risks:

- The end of the lesson becomes slightly more explicit.
- The checkpoint language must avoid sounding repetitive or preachy.

How to validate:

- Browser-QA the live `3.2 -> 3.3 -> 3.4` sequence with a fresh setup state.
- Compare first-run success in `3.4` before and after the handoff is tightened.

## Trade-offs and Decisions

- I would keep this lesson small. The issue is not that `3.3` needs more theory; it needs more truthful verification.
- I would prioritize structured proof over richer visual polish. The main UX risk is false completion, not aesthetics.
- I would not move this work into `3.4`. Tool-stack verification belongs here because `3.4` is already doing heavier integration work.
- I would keep official docs as supporting resources, but they should sit behind repo-specific success criteria and in-product verification steps.

## Priority Plan

### P0

- Replace the three proof-free toggles with required install-verification fields.
- Tighten completion so `tooling_stack_ready` reflects actual usable setup.
- Add an explicit `3.3 -> 3.4` readiness checkpoint.

### P1

- Reframe the lesson into a sequenced setup flow.
- Use `repo_orientation_ready` to personalize the task and reduce context drift.
- Turn `tooling_notes` into a structured reusable handoff artifact.

### P2

- Refine coach/resources so each external link is paired with a local success bar.
- Browser-QA the full `3.2 -> 3.3 -> 3.4` journey on desktop and mobile with fresh setup states.

## Validation Plan

- Run authenticated browser QA on `3.3` with one fresh local environment and one already-configured environment.
- Confirm the lesson cannot be completed without real verification data.
- Review saved `tooling_stack_ready` artifacts for specificity and usefulness in `3.4`.
- Track whether `3.4` support issues shift away from missing MCP/skill setup after the change.
- Check whether students can re-open the saved artifact and quickly recover their tooling context without external notes.

## Narrative Summary

Lesson `3.3` is pointed at the right problem, but the current UX is too trust-based for a setup checkpoint. It asks the student to confirm that critical tools are installed, yet it does not require proof, local verification, or a reusable setup record. That makes the lesson easy to complete and easy to get wrong. The next pass should keep the lesson lightweight while making completion more honest: install, verify, record, then move into `3.4` with a tooling artifact that actually reduces integration friction.
