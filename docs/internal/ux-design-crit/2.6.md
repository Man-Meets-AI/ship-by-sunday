# Lesson 2.6 UX Critique: Choose a Visual Direction

## Outcome Context

### Product goal

`Ship by Sunday` needs to move a paying student from concept work into a shippable v1 over one guided weekend. Each lesson should reduce ambiguity, force a meaningful decision, and leave behind an artifact the next lesson can reliably build on.

### Surface goal

Lesson `2.6` should turn saved visual references plus rough-screen intent into one usable `visualguide.md` artifact that can guide Build and make `2.7` feel like a clean wrap-up instead of another interpretation pass.

### Business model

This is a paid product with gated delivery through Stripe, Clerk, and Convex. The lesson succeeds when students feel the system is helping them make sharper product decisions, not just asking them to shuttle text between tools.

### Business metrics that matter here

- `2.5` to `2.6` continuation rate
- `2.6` completion rate
- `2.6` to `2.7` continuation rate
- time from `2.6` page load to first saved direction note
- time from first note save to saved `visualguide.md`
- percentage of `2.7` entries with a usable visual guide instead of thin filler text
- support/refund signals around “I did not know what to write in the direction note”
- percentage of Build starts that still drift stylistically despite a completed `2.6`

### Assumptions and confidence

- Assumption: this lesson is intended to create a practical build artifact, not just a reflection exercise.
- Assumption: the reference gallery from `2.1` may contain images only, without written rationale attached to each reference.
- Assumption: the embedded video may still be pending, because the lesson coach content comes from `createPendingLessonCoach`.
- Confidence: high on the structural UX issues because they are visible in the lesson contract, prompt-import logic, and workbench implementation; medium on severity in live use because this pass did not include authenticated browser QA.

## Problems I Notice

### 1. The lesson asks for a sophisticated design judgment, but the first input is one unstructured textarea.

User cannot easily translate “choose a visual direction” into a high-quality note, causing vague or overloaded input, because the page asks for hierarchy, typography feel, surfaces, contrast, spacing, trust cues, interaction tone, and what to avoid in a single freeform field with no scaffold or examples.

Impact:

- Students who are not confident in design language will either freeze or write generic taste words.
- The generated prompt quality becomes highly sensitive to writing skill rather than product judgment.
- Weak notes create weak `visualguide.md` output even when the references are good.

### 2. The reference gallery shows what the student saved, but not why those references matter.

User cannot quickly connect each image to the design shifts they actually want, causing shallow pattern extraction, because the gallery is a read-only image grid with no captured rationale, labels, or “steal this / avoid this” framing on the page.

Impact:

- Students have to reconstruct intent from memory instead of reading their own prior reasoning.
- The lesson risks turning “review references” into passive mood-boarding instead of deliberate design selection.
- The prompt can stay visually anchored while still being strategically under-specified.

### 3. The AI assist flow is operationally correct but still cognitively fragmented.

User has to understand note-writing, prompt generation, external tool switching, pasteback formatting, and markdown cleanup as separate mental steps, causing unnecessary overhead, because the workbench splits the flow across a direction note card, a generic prompt-import card, and a final markdown field without a strong sense of state progression.

Impact:

- The student can lose track of where they are in the workflow.
- Copy/paste mechanics compete with the design decision the lesson is supposed to teach.
- A lesson meant to reduce ambiguity can feel like a mini tool-ops exercise.

### 4. The completion gate checks presence, not usefulness.

User can complete the lesson with low-signal text and low-quality markdown, causing a fragile handoff into `2.7` and Build, because the artifact preview and completion logic only depend on a non-empty direction note plus some markdown with a title-like heading.

Impact:

- Students can unlock the next step with a guide that is technically saved but operationally useless.
- The product risks false confidence at a key handoff point between Design and Build.
- Downstream lessons may inherit vague style direction that the system never catches.

### 5. The top-of-page layout gives equal weight to watching and references even when the lesson’s job is synthesis.

User may read the page as “watch first, maybe review references” instead of “synthesize references into a build rule-set now,” causing weaker momentum, because the first row presents the video card and reference gallery as parallel surfaces with no stronger visual emphasis on the actual decision-making activity.

Impact:

- The student’s attention is pulled toward content consumption instead of artifact creation.
- If the video is missing, half of the hero area becomes a placeholder at the exact moment the page should feel highly actionable.
- The most valuable surface on the page, the guide-making workflow, starts below the fold on smaller viewports.

### 6. The lesson does not show what a “good” `visualguide.md` feels like before asking the student to generate one.

User cannot confidently judge whether the returned markdown is sharp enough, causing over-acceptance of mediocre output, because the page provides structure and import rules but no visible rubric, example excerpt, or checklist for evaluating the generated guide.

Impact:

- Students may paste back whatever the agent returned without editing.
- `2.7` can inherit noise, repetition, or vague brand language.
- The product teaches the mechanics of generation better than the judgment of curation.

## Solutions I Recommend

### 1. Replace the single direction note textarea with a short structured capture.

What to change:

- Break the note into 3-5 compact prompts:
  - `What should the interface feel like?`
  - `What should the hierarchy emphasize?`
  - `What UI/surface cues should repeat?`
  - `What should the build avoid?`
- Keep a final optional freeform field for any nuance.

Why it solves the user problem:

- It converts abstract taste into clearer signals the prompt can reliably use.
- It lowers the activation energy for less design-confident students.

How it supports business growth:

- Better guide inputs should raise `2.6` artifact quality and reduce downstream confusion.
- The lesson will feel more coach-like and less blank-page-dependent.

Trade-offs or risks:

- Adds more fields to a lesson designed to stay lightweight.
- Over-structuring could make advanced students feel constrained unless the fields stay concise.

How to validate:

- Compare median note length and quality before and after the change.
- Review whether `2.7` artifacts show more specific and less repetitive visual guidance.

### 2. Add “why this reference matters” context directly into the page.

What to change:

- Surface a compact annotation layer alongside the gallery:
  - selected pattern cues
  - repeated motifs
  - optional `use this / avoid this` tags
- If `2.1` does not capture rationale yet, allow a light inline annotation step inside `2.6`.

Why it solves the user problem:

- It turns the gallery from inspiration storage into decision support.
- It helps students translate images into buildable rules.

How it supports business growth:

- Stronger continuity across Design lessons increases trust in the system.
- Better prompts should yield fewer weak AI-generated guides and fewer support questions.

Trade-offs or risks:

- Pulling rationale capture into `2.6` may duplicate some intended `2.1` behavior.
- Extra annotation UI can bloat the page if it is not kept terse.

How to validate:

- QA whether a student can explain the chosen visual direction from the page without opening prior lessons.
- Sample saved guides and check whether they cite specific visual patterns rather than generic adjectives.

### 3. Reframe the workbench as a visible three-step state machine.

What to change:

- Make the main workflow explicit as:
  - `1. Define direction`
  - `2. Generate / copy the guide prompt`
  - `3. Review and save visualguide.md`
- Collapse completed steps and show one dominant CTA per stage.
- Keep success feedback persistent enough that the student knows the current step is complete.

Why it solves the user problem:

- It reduces the feeling of juggling multiple unrelated cards.
- It makes the lesson read like one guided action rather than a set of controls.

How it supports business growth:

- Faster completion with less confusion should improve throughput into `2.7`.
- The product feels more premium when the workflow itself teaches the sequence.

Trade-offs or risks:

- Requires more custom work than the current reusable prompt-import pattern.
- Could diverge from other prompt-import lessons unless the pattern becomes shared.

How to validate:

- Run browser QA and measure whether students hesitate less between note entry and pasteback.
- Review support logs for fewer questions about “what do I do next?”

### 4. Add a quality rubric before allowing completion.

What to change:

- Require lightweight checks such as:
  - guide names a clear hierarchy direction
  - guide includes concrete guidance for typography, spacing, and surfaces
  - guide includes a meaningful “what to avoid” section
- Optionally detect the expected markdown headings before marking the lesson ready.

Why it solves the user problem:

- It turns completion into “usable artifact saved” instead of “some text exists.”
- It teaches the student what a strong guide actually contains.

How it supports business growth:

- Improves the quality of the Build handoff without requiring manual review.
- Reinforces trust that course progression reflects real readiness.

Trade-offs or risks:

- Heading validation can become brittle if it is too literal.
- More gating may feel pedantic unless the rubric is clearly explained.

How to validate:

- Compare `2.7` artifact quality and Build-start clarity after adding the rubric.
- Watch whether completion drop-off rises materially; if it does, loosen the strictness while keeping the rubric visible.

### 5. Promote synthesis above watch-mode parity.

What to change:

- Move the workflow card above the fold and demote the video/reference row into supporting context.
- If no video is attached, replace the placeholder with a concise written fallback that teaches what a good visual direction guide should accomplish.

Why it solves the user problem:

- It aligns page hierarchy with the actual job to be done.
- It prevents the hero area from feeling half-placeholder, half-gallery.

How it supports business growth:

- Stronger action hierarchy should improve momentum in a paid product where students expect guided progress.
- The lesson will still work when media is incomplete.

Trade-offs or risks:

- This changes the feel of the current lesson shell and may reduce consistency with adjacent lessons.
- If the video becomes excellent, it still needs a strong placement without retaking over the page.

How to validate:

- Run desktop and mobile QA to confirm the first screen now makes the next action obvious.
- Compare time-to-first-edit in the direction note before and after the layout change.

### 6. Give students a rubric for editing the returned guide.

What to change:

- Add a short “before you save” checklist next to the markdown field:
  - remove generic brand fluff
  - keep guidance concrete enough for a coding agent
  - make sure the guide matches the saved references
  - cut anything that feels like a full design system
- Optionally show one short good-example excerpt.

Why it solves the user problem:

- It teaches curation, not just generation.
- It helps the student judge whether the output is ready for Build.

How it supports business growth:

- Better edited artifacts should produce more consistent build outcomes.
- The course feels more opinionated and valuable when it trains quality judgment explicitly.

Trade-offs or risks:

- Example excerpts can accidentally become templates students copy too literally.
- Too much rubric language can make a short lesson feel heavy.

How to validate:

- Inspect a sample of saved guides and measure how often they contain vague filler language.
- Check whether `2.7` and Build handoff docs become tighter with less redundant cleanup.

## Trade-offs and Decisions

### Keep the core artifact idea; improve the judgment scaffolding.

The current lesson direction is fundamentally right: `2.6` should produce one reusable guide file, not a full design system. The biggest weakness is not the artifact choice but the lack of intermediate UX structure that helps students make good inputs and spot bad outputs.

### Favor lightweight structure over heavier proof collection.

This lesson does not need screenshot uploads or multi-step verification. It does need better scaffolding and better completion criteria. The highest-leverage move is to improve quality without turning a 5-7 minute synthesis step into a production ceremony.

### Treat prompt import as an implementation detail, not the main event.

The course value here is design judgment. Copy, generate, pasteback, and markdown import should support that outcome quietly. The UI should stop foregrounding the mechanics more than the decision.

## Priority Plan

### P1

- Replace the single note textarea with a compact structured direction capture.
- Add a visible “review before saving” rubric beside the markdown field.
- Tighten completion readiness so low-signal or malformed guides do not unlock the next step.

### P2

- Reframe the page into a clearer staged workflow with one dominant action per step.
- Surface reference rationale or lightweight annotation so the gallery supports judgment, not just recall.

### P3

- Rebalance the top-of-page layout so synthesis is above the fold.
- Add a stronger no-video fallback or a short example excerpt for guide calibration.

## Validation Plan

- Run authenticated browser QA on `2.5 -> 2.6 -> 2.7` for desktop and mobile.
- Measure time from `2.6` load to first note save and first saved `visualguide.md`.
- Sample saved `visualguide.md` artifacts for specificity, section completeness, and alignment to references.
- Review `2.7` handoff quality to see whether Build receives cleaner, more actionable visual direction.
- Watch for any increase in drop-off after stronger validation; if it appears, trim strictness but keep the rubric.

## Narrative Summary

Lesson `2.6` is directionally strong: it turns Design references into a concrete artifact and gives the student a real handoff into the wrap-up. The weakness is that the experience still relies too much on the student already knowing how to make and judge good design direction. Right now the page is better at storing a generated guide than coaching a student toward a sharp one.

The next iteration should keep the same artifact but improve the UX around judgment. Structure the note. Make the workflow feel sequential. Teach what “good enough for Build” looks like. Tighten the completion bar just enough that `2.7` inherits a usable visual guide instead of a technically saved one.
