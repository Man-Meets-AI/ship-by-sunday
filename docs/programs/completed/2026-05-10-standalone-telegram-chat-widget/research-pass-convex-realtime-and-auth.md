# Standalone Telegram Chat Widget Convex Realtime And Auth Research

This research pass records the Convex facts that matter for the standalone widget's realtime adapter.

## Convex Realtime Facts

Convex React clients subscribe through Convex queries. `useQuery` re-runs when the query result changes, so a message transcript query can update the UI without a manual WebSocket implementation. Official docs describe Convex as a realtime database and the React client as the normal way to subscribe to query results.

The widget should not build its own WebSocket transport for Convex-backed chat. The Convex client already owns connection management, subscription identity, retries, and result invalidation.

Relevant docs:

- Convex realtime: `https://docs.convex.dev/realtime`
- Convex React client: `https://docs.convex.dev/client/react`
- Convex data flow: `https://docs.convex.dev/understanding`
- Convex function validation: `https://docs.convex.dev/functions/validation`

## Existing Host Capability

`apps/web/platform/convex/convex-client-provider.tsx` already creates a `ConvexReactClient` and wraps the web app with `ConvexProviderWithClerk`. `apps/web/app/layout.tsx` already includes that provider.

That means the Ship by Sunday web app can host a Convex-backed widget without a package-specific server and without manual WebSocket wiring.

## Auth And Session Model

Convex functions can use authenticated identity when Clerk auth is present. This is useful for signed-in customers, but anonymous homepage visitors still need a conversation authority.

The current support implementation uses an HttpOnly support-session cookie as anonymous transcript authority. That model is safer than a JavaScript-readable long-lived token, but direct browser-to-Convex subscriptions cannot read the cookie.

The standalone direct-Convex adapter needs one of these authority models:

1. Keep a host server bridge for transcript-bearing anonymous reads and writes. This preserves HttpOnly cookie authority, but does not remove the route dependency for anonymous users.

2. Mint a scoped browser-visible conversation capability. The token must be high-entropy, generated by the backend, stored only as a hash in Convex, scoped to one support conversation, validated on every query and mutation, and rotated or expired when appropriate.

3. Require signed-in identity. This is too narrow for the homepage support use case and should not be the default.

The practical Program direction is to keep fetch plus HttpOnly bridge for the first extraction, then design a scoped conversation capability for direct Convex realtime as a later slice. Clerk identity can be attached as optional metadata or used for signed-in workspace support.

## Adapter Implications

The package should expose a Convex adapter entrypoint that accepts generated Convex API references from the host. The core package should not import `apps/web/convex/_generated/api`.

The Convex adapter should support:

- query subscription for transcript state
- mutation for starting or reusing a conversation
- mutation for sending visitor messages
- optional upload/storage mutation flow
- skip behavior while the adapter does not yet have a conversation capability
- explicit loading, sending, delivery-failed, closed, and disabled states

The adapter should not:

- use Convex Component packaging
- require Convex local mode
- expose raw long-lived session tokens
- import app-specific Convex generated modules from the package core
- send transcript text to analytics

## Open Design Questions

The first child ExecPlan should not solve all realtime authority questions. It should record the target API and leave the direct Convex token model for a later adapter slice.

The main open question is whether Ship by Sunday should eventually migrate anonymous support from HttpOnly cookie bridge to scoped browser-visible conversation token. That is the cost of a truly route-free direct Convex adapter for anonymous homepage chat.
