# Planning Brief 2: Install Worker Foundations

The first child ExecPlan should be titled `Install Worker Foundations`.

The goal is to add a real product command that starts the transition from wrapper-only docs tooling to visible repo-local Worker Foundations. The customer command shape is `shipbysunday install`, with `shipbysunday i` as the short alias. Users should not see or choose profiles in the golden path. Internal bundle metadata can exist, but the default bundle is Worker Foundations.

The primary distribution path is a licensed native `shipbysunday` executable. Package-manager delivery can remain a development, bootstrap, or fallback path, but customer docs and smoke should treat the native executable as canonical. The installer should validate that it is running in a Git repo with a root `package.json`, check that the worktree is clean before mutation, verify license state under `~/.worker/` after basic repo validation and before source writes, then create or reuse the `shipbysunday/install` branch. Reuse is allowed only when the current branch is already `shipbysunday/install` with a clean worktree, or when an existing `shipbysunday/install` branch is equal to or an ancestor of the current clean base and can be checked out safely. If that branch contains unmerged prior installer work, block with a message to review, delete, or merge the branch before rerunning. If license activation is missing in interactive mode, the installer should show a one-time code, open or print a short activation URL, let the user sign in through the existing web account/access system, and poll until the server returns a revocable machine credential for `~/.worker/`. Noninteractive mode should block with setup instructions instead of trying to prompt. Repo pairing tokens are not the v1 license mechanism, and pasted license keys are deferred to a later support fallback.

The installer should present a grouped interactive confirmation checklist with customer-readable required phases such as Worker runtime, Worker toolchain, Repo commands, Agent instructions, Program and ExecPlan docs, Prompt contracts, Starter Program, Validation proof, Local commit, Codex safety setup, and Auto-kickoff Codex. The customer path should not allow partial deselection because Worker Foundations needs the full set to be useful. Rows with conflicts or missing prerequisites should show concrete blocked reasons. Enter continues, and Esc cancels. Noninteractive `--yes`, `--json`, `--repo <path>`, and `--dry-run --json` modes are v1 requirements for agents, tests, and support smoke. They should run the full required install, fail on conflicts rather than prompting, preserve the same clean-worktree/license/proof gates, and emit machine-readable status. `--yes` should still auto-commit and auto-kickoff after proof passes; `--no-commit` and `--no-kickoff` are explicit developer/test escape hatches, not part of the normal customer path.

Codex is a customer prerequisite, and auto-kickoff should not rely on whatever the user's default Codex config happens to allow. Because auto-kickoff is part of the normal customer promise, missing or unauthenticated `codex` should block before repo writes and before creating `shipbysunday/install`, with exact setup instructions. The preflight should require `codex` on `PATH`, `codex --version` success, `codex login status` success, and no explicit untrusted Codex state for the target repo. Do not use `auth.json` file presence as the authentication check because keyring-backed auth may remove that file. `codex exec` can remain a tests/support proof helper, but the foreground kickoff path should not depend on it.

The installer should install or refresh internal Worker-managed Codex permission profiles before repo mutation. These profiles are not user-facing install choices. Write them into a marked Shipbysunday-managed block in `~/.codex/config.toml`, parse and preserve unrelated Codex config, create a backup before write, update only the managed block, and roll back on failure. The v1 profile names should be `shipbysunday-worker-readonly` and `shipbysunday-worker-project-write`. The project-write profile should scope writable filesystem access to the target repo, deny environment access by default, disable agent network access unless a later proof explicitly needs it, and keep Codex's normal approval behavior for writes. If profile installation or refresh is blocked, the normal customer path should block before repo mutation with exact setup instructions. Developer/test callers may pass `--no-kickoff`; that path should not be described as the normal customer install.

Auto-kickoff should run after proof and local commit succeed unless `--no-kickoff` is passed. It should start Codex in the foreground, attached to the same terminal, with a repo-relative prompt to read `AGENTS.md`, `docs/worker/install-report.md`, the starter Program, and the first active ExecPlan, then continue from that plan. The launcher should use the local `codex` CLI with the target repo as cwd, launch with `shipbysunday-worker-project-write`, and pass the kickoff prompt through stdin. It should not detach, daemonize, or capture/store transcripts. Auto-kickoff should use Codex write capability by default because it exists to continue the first active ExecPlan. Run it only after install proof and local commit succeed on the clean `shipbysunday/install` branch. Auto-kickoff should not run on dry-run or failed proof.

`--dry-run` should be target-repo and machine read-only: inspect, classify operations, show checklist/conflict state, and exit without branch creation, `.worker/` writes, package installs, lockfile changes, Codex config writes, Worker toolchain downloads, commits, or kickoff. Persistent plan files can be a later explicit `--write-plan` feature if needed. In `--json` mode, stdout should contain one JSON object and human progress should go to stderr or be suppressed. The JSON may include repo-relative paths, required phase statuses, conflicts, planned operations, proof command statuses, branch and commit result when applicable, kickoff status when applicable, and report/proof refs. It must not include raw logs, absolute paths, secrets, package script bodies, dependency versions, source snippets, or Codex transcripts. Exit codes should be stable: `0` for `ready` dry-run or `installed` install success, `1` for `failed` unexpected errors or validation failures after writes, `2` for `blocked` known prerequisites or conflicts before writes, and `130` for `cancelled`. JSON output should always include the matching `outcome` string.

The installed source should use the product names chosen during design: `apps/worker`, `scripts/run-worker.sh`, and `.worker/`. The old `.sbs` local-runner artifact root and the old Worker/Arena names `apps/runtime`, `scripts/run-runtime.sh`, and `.runtime` are not compatibility targets for this greenfield install path. `<repo>/.worker/` is ignored repo-local state, protected through `.git/info/exclude` and `.worker/.gitignore`. Machine-level license, account, machine identity, and future non-repo secrets belong outside the target repo under `~/.worker/`, not under `<repo>/.worker/`. Tests, CI, and support smoke may override the machine state home with `SHIPBYSUNDAY_WORKER_HOME`; the default customer path should not require that variable.

The target repo should receive a self-contained Bun-first Worker package under `apps/worker`. Root `package.json` should only receive forwarding scripts that can be run through the target repo's existing package manager. Do not add `apps/worker` to the customer workspace configuration in v1. The installed Worker package should include its own `package.json`, committed `bun.lock`, focused tests, and `apps/worker/worker-manifest.json`. The native installer should prefer an existing compatible `bun` on `PATH`, but if Bun is missing or unsuitable it should provision a pinned private Bun runtime under `~/.worker/toolchains/` and use that for `apps/worker` dependency installation and proof. `scripts/run-worker.sh` should discover Bun through `SHIPBYSUNDAY_WORKER_HOME`, the default `~/.worker/` layout, or a compatible `bun` on `PATH`; it should not require a global Bun install. If the Worker-managed Bun toolchain cannot be provisioned, block before repo writes with a clear setup instruction.

The root command surface should be canonical and small: `programs:lint`, `plans:lint`, `markdown:lint`, `docs:validate`, `program:write-child-plan`, `execplan:write`, `execplan:grill`, `execplan:build`, `execplan:validate`, and `worker:test`. Do not expose `execplan:feature` in v1. The product is installing a strong repo-local operating system so Codex can work correctly, not running an automatic feature builder during install.

`scripts/run-worker.sh` should `cd` into `apps/worker`, resolve the Worker-managed Bun runtime, and run `bun run "$@"`. It may load `.env`, `.env.local`, and optional `.worker/bootstrap.env` when present, but it must not print values. Worker proof and reports must treat environment-derived data as sensitive and must not include absolute toolchain paths.

The installer should create or update root `AGENTS.md` by managed Worker section only. If root `AGENTS.md` is missing, create a concise one. It should also install nested `AGENTS.md` files under `docs/programs/`, `docs/exec-plans/`, and `docs/prompts/` so coding agents read local surface-specific rules before editing Programs, ExecPlans, or prompts.

The installer should be create-only by default and should update only recognized managed sections. Same-name owner-authored files should block with a conflict report instead of being overwritten. Rerunning `shipbysunday install` should act as same-version repair or refresh: detect the installed Worker version, refresh managed sections, repair missing generated files, reinstall `apps/worker` dependencies if needed, and rerun validation. Version identity has two fields: `installerVersion` for the native `shipbysunday` executable build and `workerBundleVersion` for the installed `apps/worker` template/source version. Repair/refresh should compare `workerBundleVersion`, not `installerVersion`, so installer fixes can ship without forcing Worker bundle migrations. If `apps/worker/worker-manifest.json` reports an older or newer `workerBundleVersion` than the bundled installer version, v1 should block with `upgrade-required` or `version-mismatch` and route to a future `shipbysunday upgrade` path instead of inventing migration semantics during install. Ownership should be tracked through `apps/worker/worker-manifest.json` for tracked installed source and `.worker/install-manifest.json` for local install/proof state. Neither manifest may store secrets, raw logs, local absolute paths, source snippets, package script bodies, dependency versions, or Codex transcripts.

The installer must dogfood the result. It should create a real repo-specific Worker Foundations adoption Program packet, then call the installed `program:write-child-plan` command to create the first child ExecPlan. That proves the forwarding script, Bun Worker package, Program packet validation, immutable planning brief resolution, and child-plan writer. After dogfood, run the installed validation commands: `programs:lint`, `plans:lint`, `markdown:lint`, `docs:validate`, and bounded `execplan:validate` proof. Run `worker:test` as install/repair proof, but keep Worker runtime tests separate from ordinary `docs:validate`.

The installer should write detailed local proof under `.worker/` and a concise tracked report at `docs/worker/install-report.md`. The tracked report is overwritten on same-version repair/refresh so agents have one obvious current install state; durable run-by-run proof belongs under ignored `.worker/runs/<run-id>/`. The report should include installed version, files added, commands run, validation results, auto-kickoff status, next Codex prompt, and a suggested CI snippet. It must not include raw logs, absolute paths, secrets, package script bodies, dependency versions, source snippets, or transcripts. Do not patch `.github/workflows/**` in v1.

Auto-commit is part of the default customer experience. After all required phases and validation proof pass, commit locally on `shipbysunday/install` with `feat(worker): install planning operating system`. If validation fails or proof is blocked, leave the branch uncommitted with an incomplete install report and exact failing commands. Do not push or open a pull request by default.

Implementation should start in `packages/local-runner/src/cli.ts` and new local-runner workflow modules under `packages/local-runner/src/workflows/worker-foundations-install/` or an equivalently specific name. Tests should cover inspect, checklist modeling, branch handling, license gating, Bun prerequisite behavior, apply, dogfood, validation, auto-commit, idempotent rerun, and conflict behavior with sparse fixtures, existing docs-core fixtures, and an Arena-harness fixture. Avoid writing to the real Arena checkout in automated tests unless the command is explicitly pointed at a disposable clone or fixture.

Focused validation should include local-runner tests for the new command, docs operating-system regression tests, local-runner build, package smoke when the binary shape changes, Program lint, plan lint, markdown lint for this Program and child plan, and `git diff --check`.
