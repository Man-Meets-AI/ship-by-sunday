# Telegram Support Bot Planning Brief 1

The first child ExecPlan should be titled `Homepage Widget And Telegram Bridge Proof`.

The goal is to prove the core loop end to end: a visitor opens the homepage support widget, sends a message without leaving the site, Parker receives that message in Telegram through a dedicated support bot, Parker replies in Telegram, and the visitor sees the reply in the website widget.

Exact scope: add dedicated support-bot env names and setup docs, add the Convex support visitor/thread/message schema and validators, add retention fields for idle-close and purge eligibility, add an HttpOnly anonymous visitor support session cookie with Convex-stored token hashes, add first-slice abuse controls, add the minimum Next support-session route handlers, Convex mutations/queries/actions, and Convex HTTP actions needed for lazy first-message thread creation and store-first message delivery, add a homepage support widget behind the homepage content/render-model boundary, add a Telegram webhook boundary, create one Telegram forum topic per support thread, post visitor messages into the support operator topic after persisting them in Convex, ingest allowed Telegram operator replies back into Convex, and render live replies in the widget.

The first slice must not reuse `TELEGRAM_BOT_TOKEN` or `TELEGRAM_CHAT_ID`; those are observability-owned. Use customer-support-specific names. The exact names can be selected by the ExecPlan, but they should read like `TELEGRAM_SUPPORT_BOT_TOKEN`, `TELEGRAM_SUPPORT_CHAT_ID`, `TELEGRAM_SUPPORT_WEBHOOK_SECRET`, `TELEGRAM_SUPPORT_OPERATOR_USER_IDS`, and `TELEGRAM_SUPPORT_ADMIN_RECOVERY_TOKEN` unless the repo already has a stronger naming convention by then.

Those support values should be Convex env values because the Telegram webhook and delivery path run through Convex HTTP actions. The setup doc should live in app docs and cover BotFather bot creation, dedicated private supergroup with forum topics enabled, exact bot admin permissions, webhook URL construction from `NEXT_PUBLIC_CONVEX_SITE_URL`, local/preview/production ownership, verification steps, and failure modes. It must name `setWebhook.secret_token`, the incoming `X-Telegram-Bot-Api-Secret-Token` header, Telegram's 1 to 256 character secret-token constraint using only `A-Z`, `a-z`, `0-9`, `_`, and `-`, `allowed_updates` limited to `message` and `callback_query`, `getWebhookInfo` checks, `can_manage_topics` for topic creation and closing, and `can_delete_messages` for deleting forum topics during retention cleanup.

The Telegram webhook should be a Convex HTTP action because Convex owns support state and the repo already uses Convex HTTP actions for provider webhook surfaces that mutate Convex. Keep the boundary narrow and document the exact path, secret-token verification, allowed updates, and failure responses. Missing or wrong secret headers should deliberately return non-2xx, invalid JSON can return 400, and authenticated unsupported updates should return 200 ignored responses so Telegram does not retry unsupported Slice 1 shapes indefinitely.

The widget should be homepage-only in this slice. It should not render on protected workspace routes yet. It should use Ship by Sunday's visual system, avoid third-party widget scripts, use a narrow Next support-session bridge for transcript reads and visitor sends, support desktop and mobile placement, avoid covering checkout/demo controls, and expose a fallback link to `https://t.me/parkerrex` only if the bridge is unavailable or the user intentionally chooses Telegram. The route bridge should mint or read a `__Host-sbs_support_session` cookie with `HttpOnly`, `SameSite=Lax`, `Path=/`, no `Domain`, and `Secure` in production; the widget must not store the raw support token in localStorage. Opening the widget should not create a durable support record; the first real visitor message should create the visitor, thread, Telegram topic, and first support message. Do not require email before that first message, and do not add a dedicated contact/email field, email validation gate, or separate lead form step in Slice 1. Visitors can type contact details naturally in chat; an explicit `Ask for email` flow belongs to a later structured operator action. The widget should be passive and on-demand: no auto-open, no timed popup, no fake online state, a quiet fixed launcher, a compact desktop panel, and a mobile bottom sheet. Visitor-facing launcher and header copy should be Parker-first, such as "Message Parker" or "Ask Parker"; system, error, disabled, and fallback states can say "Ship by Sunday support." Starter copy should set asynchronous expectations: invite questions about fit, setup, checkout, or the visitor's codebase, say Parker will reply in the widget when available, and avoid green dots, "online" labels, and response-time promises.

If the visitor is already signed in, Slice 1 may attach `clerkUserId` as optional support metadata on the visitor or thread. Do not make signed-in status a requirement for support. Do not let Clerk identity replace the HttpOnly support session cookie as the widget read/write authority. Account-level support history belongs to a later authenticated-support slice.

The first slice should be CAPTCHA-free. Abuse controls should be Convex-side: one open thread per anonymous support session, message length cap, per-session send cooldown, pending visitor message cap before operator reply, global hourly send cap, and a support kill switch that turns the widget into the fallback Telegram link. Turnstile or another CAPTCHA belongs in a later hardening slice only if actual spam justifies the provider setup and UX friction.

The first slice should be text-only. Accept plain text and links as text. Do not support image upload, file upload, screenshots, voice notes, or binary attachments. Telegram-side media messages should not become website-visible support replies in Slice 1. Future attachment support needs a separate storage, privacy, retention, and Telegram file-mapping decision.

Visitor sends should persist before Telegram delivery. The widget should render clear delivery states such as `sending`, `delivered_to_parker`, and `delivery_failed`. If Telegram delivery fails, the message remains in Convex, the visitor sees a fallback Telegram link, and the backend records safe delivery-error metadata for retry or debugging without sending message text to analytics.

Do not add automatic background retries in Slice 1. Store delivery attempt count, last delivery error, and last delivery attempt time, then provide a maintainer-only Convex recovery action that retries one stored failed visitor message after setup repair. Protect that action with `TELEGRAM_SUPPORT_ADMIN_RECOVERY_TOKEN`; do not reuse the webhook secret, observability token, or Telegram operator allowlist as its only authority. Setup docs should explain common delivery failures such as missing env, wrong chat id, missing bot membership, missing forum-topic permissions, invalid webhook secret, and missing recovery token.

Analytics in the first slice should be metadata-only. It can use the existing PostHog client path for lifecycle events such as widget opened, thread created, message sent, reply received, send failed, and fallback clicked. Safe properties include page path, thread status, delivery status, and error class. Do not send message bodies, emails, Telegram ids, visitor tokens, or transcript text to PostHog. Also prove session replay privacy by asserting rendered transcript DOM has `data-ph-no-capture` or the equivalent block selector and message inputs have `data-ph-mask`, `data-sensitive`, or the equivalent mask selector.

The Telegram side should use a private support supergroup with forum topics enabled and support normal replies first. A normal message from an allowed operator inside a mapped support topic should become a visitor-visible reply. The only Slice 1 button should be `Close thread`, which proves callback parsing, operator allowlisting, support action audit, thread lifecycle mutation, and website closed-state rendering. Do not ship AI drafts, prompt generation, checkout links, Linear drafts, canned customer-visible sends, or customer-visible AI auto-replies in this slice.

Telegram topic titles should use generated support ids and safe routing metadata only, for example `SBS-0421 · homepage · May 6`. Do not put visitor names, emails, message text, product details, or other user-supplied content in the topic title. Put richer context inside the first bot message in the topic instead.

Every Telegram topic should start with a bot-authored context header before the first visitor message. Include safe operator context: support id, entry surface/path, date, visitor kind (`anonymous` or `signed-in`), delivery status, and the `Close thread` button. Do not include the visitor token, raw email, message text, or hidden identifiers that do not help Parker operate the thread.

The slice must include external setup docs with what to create in Telegram, where to create it, exact bot and chat requirements, environment ownership for local, preview, and production, where values go, how to set the webhook, how to verify delivery, and what failure looks like when setup is missing or misconfigured.

Focused validation should include unit tests for support session cookie handling, support session routes, support validators, Telegram update parsing, and delivery classification; Convex model tests for support thread/message lifecycle and abuse limits; integration tests for the webhook route/action; integration-ui tests for widget open/send/failure/closed states and replay-masking attributes; and desktop/mobile browser proof of the homepage widget. Finish with `bun run format`, `bun lint`, and `bun typecheck`. Do not require full hosted e2e unless the implementation touches auth, checkout, entitlement, release proof, or another release-sensitive path.

Retention in the first slice should be modeled even if the scheduled purge worker lands in a later hardening slice. The schema and docs should make the locked policy visible: idle anonymous threads auto-close after 14 days, closed transcript bodies retain for 90 days, purge removes Convex message bodies and deletes or marks cleanup failure for the matching Telegram forum topic, and only minimal audit metadata remains after purge.

Broader validation should include `bun run programs:lint`, the relevant app lint/format/typecheck gates, and any hosted Convex dev validation required by the touched Convex code. Do not use Convex local mode.
