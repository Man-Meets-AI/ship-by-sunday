# Research Pass: Loop Catalog And Monetization

## Question

What loop catalog should Ship by Sunday sell, which loops are most valuable, and how should the Program sequence the commercial product after the active source-contract reconciliation slice?

## Commercial Thesis

Ship by Sunday should sell one simple flagship offer for web-app progress, not a fragmented menu. The current `$250` offer, soon moving toward `$500`, should include diagnosis and the first recommended loop: find what is blocking the app, rank the highest-leverage opportunities, run the scoped worker loop that matters most, prove the result, update repo memory, and recommend the next loop.

The key shift is from "we generate a codebase" to "we diagnose and move the app forward inside one paid engagement." The loop catalog is still commercially important, but mostly as fulfillment inventory and positioning proof. A new app builder gets the new-app loop. A broken app owner gets rescue. A SaaS founder gets the revenue, reliability, or speed loop the doctor pass selects. An agency gets a repeatable way to explain what happened across client apps.

## Loop Catalog

The catalog should be broad enough to make every web-app builder feel seen, but each monetized loop needs a strict input contract, output artifact, proof path, and failure state.

### Diagnostic Loops

- Doctor pass: inspect product truth and repo truth, then return the top nine opportunities with ranked next actions.
- Broken-app triage: reproduce the failure, identify the likely root cause, and estimate repair risk before patching.
- Repo health audit: map source truth, package manager, tests, CI, routing, auth, data, release path, and known hazards.
- Release-readiness pass: compare current repo state against the commands and browser proof needed to ship.
- Architecture map: produce a source-truth map for agents, teams, or agencies inheriting an unfamiliar app.
- AI-readiness pass: identify where AI features are viable, risky, or likely to waste money.

### Rescue And Quality Loops

- Broken-app rescue: reproduce, localize, patch after permission, and prove the app is unstuck.
- Debugging loop: fix a specific bug with reproduction proof and regression coverage when practical.
- Test hardening loop: add focused unit, integration, or browser coverage around high-risk behavior.
- Flaky test repair loop: stabilize unreliable tests and document the real failure mode.
- TypeScript and lint cleanup loop: remove blocking static errors without broad refactors.
- Dependency upgrade loop: upgrade risky or stale packages with lockfile and focused regression proof.
- Framework migration loop: migrate one bounded surface across framework or routing versions.
- Refactor loop: reduce complexity in a named code path only when it unlocks delivery or reliability.
- Security patch loop: fix a specific exposed risk and document the proof and remaining limits.

### Revenue And Growth Loops

- Activation loop: improve the first successful user action after signup or checkout.
- Onboarding loop: reduce confusion in setup, first run, empty states, and first value delivery.
- Conversion loop: improve homepage, pricing, CTA, checkout handoff, or trial-to-paid path.
- Billing loop: harden checkout, subscriptions, invoices, webhooks, entitlement, and recovery states.
- Auth and access loop: harden login, signup, session, protected routes, role checks, and account recovery.
- Analytics loop: add event naming, funnel tracking, dashboard proof, and source-of-truth docs.
- SEO loop: fix metadata, sitemap, indexing, content structure, performance blockers, and search intent pages.
- Content loop: create or improve pages, docs, blog posts, lifecycle content, and launch assets.
- Email loop: add transactional or lifecycle email paths with provider setup and failure handling.
- Support ops loop: create admin visibility, support playbooks, canned responses, and issue handoff.

### Product Experience Loops

- Design loop: improve a user-facing flow with screenshots, responsive proof, and visual-system alignment.
- Mobile responsiveness loop: fix layout, overflow, tap targets, and mobile navigation across key pages.
- Accessibility loop: improve keyboard, semantics, labels, contrast, reduced motion, and screen-reader basics.
- Performance loop: reduce slow pages, expensive queries, heavy bundles, or poor Core Web Vitals.
- Admin tooling loop: add internal screens, repair tools, export flows, moderation queues, or ops dashboards.
- Navigation loop: improve information architecture, route hierarchy, breadcrumbs, and user orientation.
- Empty-state loop: make no-data, loading, error, and permission states useful and conversion-aware.

### Operations And Trust Loops

- Observability loop: add error tracking, replay, logging, alerts, and debug docs for high-risk paths.
- Release loop: prepare release proof, smoke checks, rollback notes, and operator handoff.
- CI/CD loop: repair or create the minimum trustworthy checks for the repo's actual stack.
- Documentation loop: align source truth, onboarding, setup, commands, and future-worker instructions.
- Agency/client reporting loop: produce client-ready diagnosis, progress, proof, and next-loop recommendations.
- Data migration loop: plan, backfill, verify, and document a bounded data shape or provider migration.
- Privacy and consent loop: document data flows, permission boundaries, retention, and user-facing claims.
- Compliance prep loop: collect evidence, gaps, and owner actions for a narrow compliance need.

### AI Feature Loops

- AI feature integration loop: add a scoped AI feature with provider boundaries, UX states, and cost controls.
- Prompt and eval loop: create or harden prompts, structured outputs, fixtures, and evaluation checks.
- RAG/data loop: connect a bounded knowledge source with retrieval proof and hallucination guardrails.
- AI latency and cost loop: reduce model cost, response time, retry waste, and token-heavy workflows.
- AI safety loop: add moderation, refusal, audit logging, or human-review boundaries for sensitive outputs.
- Bring-your-own AI loop: connect a supported Codex, API-key, GitHub, or local-runner execution surface with explicit consent.

## Flagship Offer And Downstream Packages

Flagship offer: the current `$250`, soon `$500`, should be the default public purchase. It should include the doctor pass, top-nine report, permission map, proof plan, selected first loop, proof output, blocked-proof report when needed, and next-loop recommendation.

Loop catalog: internal fulfillment inventory and landing-page proof, not a confusing shelf of separate first-purchase SKUs. The catalog lets Ship by Sunday route the same purchase into broken-app rescue, design, billing, auth, performance, SEO, conversion, release, analytics, observability, or another scoped loop.

Additional loop: a follow-on purchase after the first proof, sold from the updated opportunity ledger. This should feel like "run the next recommended loop" rather than a standalone product hunt.

Monthly operating subscription or repo retainer: recurring doctor refresh, loop runs, repo memory updates, proof history, and next-loop recommendations after the customer has seen the first proof.

Agency tier: the flagship offer repeated across client apps, with multi-repo diagnosis, client-ready proof reports, shared templates, operator dashboards, and permission boundaries per client.

Emergency rescue: a premium version of the flagship offer for broken production or blocked launches. It starts with read-only triage, moves to patching only with permission, and requires proof or an honest blocked report.

Concierge review: a human-reviewed version of the flagship offer for high-risk surfaces such as billing, auth, security, migrations, and production incidents.

Bring-your-own AI/Codex: margin and distribution advantage, not a consent shortcut. The customer can attach supported ChatGPT/Codex, API-key, GitHub, or local execution surfaces where available. The product must name exactly what is connected, stored, charged, and permitted before a paid loop uses it.

## Top-Nine Doctor Pass Output

Each opportunity should be structured enough to sell the next step and safe enough to block unsupported claims.

```yaml
opportunity:
  id: stable-kebab-case-id
  title: short buyer-readable title
  audience_lane: new_app | broken_app | indie_saas | agency | mature_team
  buyer_value: plain-language business value
  expected_impact:
    revenue: direct, indirect, none, or unknown
    speed: estimated builder or operator time saved
    reliability: expected reduction in risk or incidents
  confidence: high | medium | low
  confidence_reason: facts supporting the rating
  blast_radius: small | medium | large
  blast_radius_reason: affected flows, files, data, or users
  proof_path:
    commands: repo commands or checks to run
    browser_paths: pages or flows to inspect
    external_evidence: dashboard, email, analytics, payment, or provider proof
  required_permissions:
    repo_access: none | read_only | branch_write | production_write
    execution_surface: generated_repo | github | local_runner | codex | api_key | concierge
    provider_access: named third-party dashboards or secrets required
  recommended_loop: loop catalog id
  offer:
    package: flagship_included | additional_loop | subscription | emergency | agency | concierge
    price_language: buyer-facing offer phrase, usually included in the current $250 soon-$500 flagship offer
  next_action:
    label: buyer-facing command or CTA
    blocked_until: missing permission, missing fact, or proof dependency
  failure_state: what Ship by Sunday reports if proof cannot be completed
```

The top-nine report should rank opportunities with a visible scoring model:

- buyer pain
- willingness to pay
- proof clarity
- blast-radius risk
- repeatability
- next-purchase pull
- confidence from observed repo and product facts

## How Loops Compound

Every completed loop should update the same memory surfaces so the next purchase is easier to trust.

- Repo memory: update the source-truth map, command map, stack map, hazard list, and permission history.
- Program state: record the loop outcome, decision, remaining risks, and next recommended slice.
- ExecPlan state: close or refresh the child plan with validation evidence, blocked proof, and follow-up boundaries.
- Source truth: update docs, setup instructions, product facts, generated artifacts, or provider setup docs when behavior changes.
- Opportunity ledger: mark the selected opportunity as completed, blocked, superseded, or deferred, then rescore the remaining opportunities.
- Proof history: store commands, screenshots, dashboard evidence, test output, release evidence, or human review notes.
- Next-loop recommendation: recommend one primary next loop and one fallback, with the reason each follows from proof.
- Offer state: determine whether the next purchase should be the next recommended loop, subscription, retainer, agency package, or concierge review.

This compounding ledger is the moat. Random agent runs create scattered changes. Ship by Sunday should create a loop trail that makes each future loop cheaper, safer, and easier to sell.

## What Not To Claim Yet

Do not claim arbitrary repo repair is automatic. The truthful promise is diagnose first, ask for permission, run a scoped loop, and prove or report the block.

Do not imply Ship by Sunday can touch GitHub, Codex, local files, API keys, provider dashboards, production databases, or payment systems without explicit consent and setup.

Do not claim self-serve mature-repo transformation until the audit, execution-surface, adoption Program, safe patch, and proof contracts exist.

Do not claim BYO Codex eliminates cost or permissions. It changes the execution surface and margin model, but the product must still document account connection, billing, storage, rate limits, and permission boundaries.

Do not launch every catalog loop as a separate SKU. The catalog can be shown as proof of breadth, but the public first purchase should stay the simple `$250` soon-`$500` flagship offer with diagnosis, selected loop execution, and proof.

## Slice Order Implication

Keep the active source-contract reconciliation first. Immediately after it lands, the next child ExecPlan should define the commercial doctor pass and loop catalog around the flagship offer. That slice should produce the top-nine schema, loop scoring, `$250` soon-`$500` offer language, landing-page story, consent boundaries, proof contracts, and the first fulfillment-loop shortlist.

After that, harden the execution-surface contract, then ship broken-app rescue as the first existing-repo fulfillment path inside the flagship offer. The broader generated operating pack should still ship, but the catalog and doctor pass should lead because they create the common commercial language for every lane.
