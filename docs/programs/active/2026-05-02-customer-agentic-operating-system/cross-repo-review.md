# Cross-Repo Review

## Review Summary

The Program split is directionally right, but the first generated-repo slice should be source-contract reconciliation, not full operating-pack shipment. Generated repos are the right first target because the output is controlled, the package manager is known, and compiler tests can prove the contract. After that active proof, the next Program slice should move to the commercial doctor pass, loop catalog, monetization ladder, and landing-page story before broader operating-pack generalization so the initiative has a revenue wedge across new repos, broken apps, mature repos, agencies, and operators.

## Risks

The biggest risk is source-of-truth duplication. Generated customer repos already include Build Pack readiness and first-slice planning. The new Program/ExecPlan pack must connect to those docs instead of creating a second contradictory planning layer.

The second risk is leakage. Internal completed Programs, internal prompt assumptions, local release evidence, and Ship by Sunday-specific CI rules must not enter customer artifacts.

The third risk is over-automation. A hidden `postinstall` or default bootstrap mutation would make the repo dirty before the customer understands the change. Agentic bootstrap must be explicit.

The fourth risk is mature-repo overreach. Existing repos may use npm, pnpm, yarn, Python, Go, Rails, GitHub Issues, Jira, or custom CI. The adoption lane must audit and adapt instead of imposing the starter's Bun and Next.js assumptions.

The fifth risk is optional tool drift. Linear, external skills, MCPs, Codex app-server runtime, and PostHog triage are valuable later layers, but they need explicit customer setup and safety decisions. They should not become hidden prerequisites for the first generated-repo operating-system slice.

The sixth risk is worker overpromising. Worker-first language is stronger than generic agent language, but it creates a higher proof burden. A worker must have a durable role, source truth, plan state, validation standard, review proof, and loop. If the existing-codebase lane does not yet audit and install those pieces, homepage and sales copy must not imply that mature repos can self-serve the full worker layer today.

The seventh risk is burying the commercial wedge behind too much internal packaging work. The operating pack is necessary, but customers buy diagnosis, repair, and proof. The Program should therefore define the top-nine opportunity schema and loop catalog as a product artifact, not only as implementation vocabulary.

The eighth risk is BYO AI consent drift. The repo already has optional Codex app-server connection code, and official Codex docs support ChatGPT/API-key sign-in plus GitHub-connected cloud environments. That supports a "bring your own execution surface" strategy, but the product must document exactly what account, repo, permission mode, and storage boundary a loop uses.

OpenAI's current Codex docs support this ordering. Codex can work through local app, IDE, CLI, and cloud surfaces, while project-scoped config requires trusted projects. Apps SDK docs support future MCP tool distribution, but app review, privacy, OAuth, and tool-annotation requirements make it a later channel rather than a core dependency.

## Missing Work To Carry Into Later Slices

The Program needs a customer-safe prompt and skill versioning policy. If prompts are copied from internal docs, the first implementation slice must strip repo-specific references and test for forbidden internal paths.

The Program needs a mature-repo data boundary. Before product UI is built, the team must decide whether audits run locally, through a GitHub connector, through zip upload, or through a generated prompt pack that a customer's agent runs inside their repo.

The Program needs a product promise update. The public surface should say that Ship by Sunday is the agent doctor for web apps: diagnose blockers, rank fixes, run named AI worker loops, and prove results. Programs, ExecPlans, validation, and review loops should show up as the machinery that makes the promise reliable, not as the first explanation. The product should not imply that mature repos become production-ready automatically.

The Program needs a doctor-pass contract. Before UI or ChatGPT app distribution changes, define the top-nine opportunity schema, loop taxonomy, proof fields, failure states, and conversion path from diagnosis to paid loop execution.

The Program needs an execution-surface contract. Before paid loops depend on customer-owned AI, define Codex app-server, ChatGPT/Codex cloud, API-key, GitHub, and local-runner modes with consent, storage, permissions, rate limits, and fallback behavior.

## First ExecPlan Critique

The first child ExecPlan should be narrower than full pack shipment. It should reconcile the customer-facing source contract: root agent guidance, Build Pack docs, generated prompt naming, generated skill triggers, generated package-script promises, snapshot exclusions, and tests. It should not implement the mature-repo lane, even though the Program has to design for it. The first slice should end with a materialized generated repo whose current agent guidance is coherent and whose future operating-pack extension points are safe.

The next child ExecPlan after source-contract proof should be `Define Commercial Doctor Pass, Loop Catalog, Monetization, And Landing-Page Story`, not the full operating-pack shipment. That plan should produce the top-nine schema, money-ranked loop catalog, scoring rubric, proof contract, package language, consent boundaries, landing-page explanation, and commercial conversion states that later generated-repo, broken-app, and mature-repo slices can share.

## Required Validation

The first child ExecPlan should validate the package with focused compiler tests, output snapshot or materialization checks, package typecheck, package lint, package format check, Program lint, ExecPlan lint, markdown lint for touched docs, and repo diff whitespace checks.
