## Positioning Decision

Lead with this plain-language frame:

Ship by Sunday is the agent doctor for web apps. It diagnoses what is blocking your app, ranks the highest-leverage fixes, and runs proven AI worker loops to ship improvements with proof.

Do not lead with "agentic engineering methodology," "operating system," or "Programs and ExecPlans." Those are the trust machinery behind the product. The landing page should sell diagnosis, loops, proof, and the ability to use the customer's app, repo, GitHub, Codex, API-key, or local execution surface only when explicitly supported and consented.

## How It Works

1. Bring the app context.
   Start from an idea, generated repo, GitHub repo, broken app, or existing SaaS app. Ship by Sunday gathers the product goal, stack, current blockers, and supported execution options.

2. Run the doctor pass.
   The doctor pass inspects product truth and repo truth, then returns the top nine opportunities ranked by buyer value, confidence, blast radius, proof clarity, and next-loop fit.

3. Pick the loop.
   Choose a scoped loop such as broken-app rescue, design, billing, auth, performance, SEO, conversion, analytics, observability, release, tests, migration, AI integration, or agency reporting.

4. Approve the execution surface.
   The loop runs only against an approved surface: generated repo, GitHub, local runner, Codex, API key, or concierge path when supported. Missing permissions become explicit blockers.

5. Review proof and buy the next move.
   Every loop ends with a patch, artifact, proof output, browser evidence, dashboard evidence, or a blocked-proof report. The opportunity ledger updates and recommends the next loop.

## Objection Handling

### Why Not Just Use ChatGPT Or Codex Directly?

Use them when you know exactly what to ask and how to prove the answer. Ship by Sunday is for when you need diagnosis, prioritization, scoped loops, permission boundaries, proof, and repo memory. It can use supported AI/Codex execution surfaces, but the product value is the doctor pass and loop system around the model.

### Will It Touch My Repo Without Permission?

No. The doctor pass can run as a diagnosis. Any loop that reads or writes a repo, uses GitHub, runs local commands, connects Codex, uses an API key, or touches provider dashboards must name the required permission and execution surface first.

### What Do I Get After Paying?

For a doctor pass, you get the top nine opportunities, buyer value, confidence, blast radius, proof path, required permissions, recommended loop, offer, and next action. For a paid loop, you get the scoped patch or artifact plus proof output, or an honest blocked-proof report.

### Can It Fix My Existing App?

It can help existing apps through a diagnostic-first path. The truthful sequence is audit, rank, permission, scoped loop, proof. Self-serve arbitrary repo repair should not be promised until the mature-repo audit, execution surface, safe patch, and proof contracts are in place.

### What If The Loop Cannot Prove Success?

The loop should return a blocked-proof report that names what was attempted, what evidence is missing, what permission or environment blocked proof, what risk remains, and which next action would unblock validation. That report should not be marketed as a completed fix.

## Copy Boundaries

Use "diagnose," "rank," "run scoped loops," "approve permissions," and "prove" as the core verbs.

Avoid making "agentic engineering," "methodology," "operating system," "Programs," or "ExecPlans" the first explanation. Those can appear in deeper docs as the reason loops compound.

Avoid implying that the product can silently attach to Codex, GitHub, local files, API keys, Stripe, auth providers, or production systems. The landing page should make permission and proof feel like product strengths, not caveats.
