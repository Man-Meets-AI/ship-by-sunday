# Research Pass: Market Expansion And Agent Doctor Wedge

## Question

How should this Program change if the business goal is to capture as many web-app builders as possible and maximize revenue from agentic engineering loops?

## Findings

The current Program correctly identifies the worker layer as the buyer-facing product, but it still reads too much like an implementation roadmap for generated repo artifacts. The stronger commercial frame is that Ship by Sunday should become the agent doctor for web apps: diagnose the repo, prescribe the highest-leverage loops, attach the customer's execution surface, and keep running scoped work until the app improves.

The market should not be limited to people starting from a blueprint. The broadest web-app market has at least four lanes:

- new app builders who want a fresh worker-ready repo
- vibe-coded app owners whose apps are broken, fragile, or stuck
- mature indie and SaaS teams with a valued repo but no reliable agent operating layer
- agencies and fractional operators who need repeatable loops across client codebases

The acquisition wedge should be a diagnostic, not a lesson. A paid or lead-generating "goal pass" can inspect product truth and repo truth, then return the top nine highest-leverage opportunities with expected impact, confidence, blast radius, proof command, and recommended worker loop. That makes the product instantly useful even before a customer understands Programs, ExecPlans, or agentic engineering vocabulary.

The loop catalog is the monetizable product inventory. Customers should be able to buy or subscribe to loops such as:

- goal pass: rank the top nine highest-leverage opportunities
- design loop: improve UX against the product's visual doctrine and browser proof
- broken-app rescue loop: reproduce failures, localize root causes, patch, and prove
- test loop: add focused coverage around high-risk paths
- release loop: prepare release proof and smoke checks
- billing/auth loop: harden monetization and access paths
- performance loop: profile slow pages and expensive backend paths
- dependency loop: upgrade risky packages with scoped verification
- docs loop: align source truth, onboarding, and operator docs
- observability loop: add useful error, replay, and alert surfaces
- growth loop: improve homepage, pricing, activation, and conversion paths

The Program should separate "teach loops" from "sell loops." Teaching is important for retention and trust, but the purchase moment should be outcome-first: connect or generate a repo, run the doctor pass, pick a loop, review proof, and repeat. Programs and ExecPlans should remain visible as proof and durability, not as the top-level promise.

Bring-your-own AI should be treated as a strategic distribution and margin lever, but only where the integration is explicit and consented. The existing app already has an optional Codex app-server connection surface that lets paid users connect a ChatGPT/Codex subscription for in-app generation. Official Codex docs also describe signing in with a ChatGPT account or API key, and Codex cloud requires setting up an environment connected to a GitHub repository. Codex configuration supports project-scoped `.codex/config.toml` only after the project is trusted. The truthful product language is therefore "attach your execution surface" rather than "we attach to your Codex." The user should explicitly connect ChatGPT/Codex, an API key, a GitHub repo, or a local repo runner before any loop can act.

ChatGPT Apps and MCP can become a later distribution lane. Official Apps SDK docs describe exposing tools and optional UI resources from an MCP server so ChatGPT can drive the app, with OAuth added only when user-specific data or write actions require it. That suggests a future Ship by Sunday ChatGPT app could expose doctor, opportunity ranking, loop selection, and status tools. It should not be a first dependency for the current Program because app review, privacy disclosures, tool annotations, and OAuth requirements add launch risk.

The strongest monetization model is layered:

- diagnostic: low-friction paid or lead-generating goal pass
- loop execution: per-loop purchase for broken-app rescue, design, billing, release, and growth loops
- subscription: ongoing worker operating layer for recurring loops and repo memory
- agency/team tier: multi-repo loop management, review evidence, and client reporting
- premium concierge: human-reviewed execution for high-value or high-risk repos

The current public offer already has a paid generated-codebase path. The better approach is not to wait until every operating-system artifact is generalized before testing a bigger market. After the active source-contract slice, the next revenue-oriented slice should define the doctor pass and loop taxonomy so the product can sell diagnosis and repeatable loops while generated-repo packaging continues in parallel or immediately after.

The doctor pass should become the shared checkout handoff. Whether the customer starts from the homepage Blueprint, a broken existing repo, a GitHub import, or a concierge intake, the first paid experience should answer:

- what is the app trying to become?
- what is the current repo or generated repo capable of today?
- what are the top nine highest-leverage opportunities?
- which loop should run first?
- what proof will convince us the loop worked?
- what permissions or execution surface are required?

The top-nine report should be opinionated enough to sell the next step. Each opportunity should have an expected buyer value, a confidence rating, a risk or blast-radius rating, the first proof command or browser proof, the recommended loop, and a "buy/run now" path when the required execution surface is connected.

The highest-leverage product move is to make every lane converge on one loop ledger. New generated repos, existing repos, and broken apps should all end with the same artifact shape: a source-truth snapshot, opportunity ranking, selected loop, ExecPlan, proof, and updated source truth.

## Commercial Architecture

The product ladder should be:

1. Free or low-friction lead: explain the app and optionally paste a repo/GitHub URL for a lightweight opportunity preview.
2. Paid first pass: run the full goal pass or generated-repo pass and return the top nine opportunities.
3. Paid loop: run one scoped loop with proof, such as broken-app rescue, design, billing/auth, release, or growth.
4. Subscription: keep the repo under an operating layer with recurring loop runs, source-truth updates, and review evidence.
5. Concierge/team tier: human-reviewed loops, multiple repos, agency reporting, and higher-risk work.

This ladder captures people who want a new codebase, people whose existing app is broken, and teams that already have a product but need repeatable worker leverage. The common unit is not "lesson consumed"; it is "loop completed with proof."

The first self-serve loop to monetize outside generated repos should be broken-app rescue. The pain is obvious, the proof is concrete, and the loop naturally demonstrates the operating system: reproduce, localize, patch, prove, and update source truth. Design loop is the second-best self-serve candidate because it is visually legible and can use browser proof. Billing/auth and release loops are high-value but need stricter setup and safety boundaries.

The moat is compounding repo memory and loop evidence. A one-off agent can patch a bug. Ship by Sunday should preserve the source-truth map, opportunity ledger, selected loop, proof, and next recommendation so each run makes the next run easier to trust.

## Slice Order Implication

Keep the active generated-repo source-contract reconciliation first because it is already started and protects current customer output. After that, move the doctor pass and loop taxonomy ahead of broader operating-pack generalization. The operating pack still matters, but the doctor pass creates the revenue wedge and the common language for every later artifact.

Recommended next order after the active child ExecPlan:

1. Define doctor pass and loop taxonomy.
2. Harden BYO execution surface for Codex, API keys, GitHub, and local runners.
3. Ship broken-app rescue loop.
4. Ship customer-safe operating system file set.
5. Add explicit generated repo agentic bootstrap.
6. Define the public worker-led lane journey.
7. Design and implement mature-repo adoption.
8. Explore ChatGPT app distribution after the loop engine is stable.

## Recommended Direction

Reframe the Program as the Agent Doctor and Loop Operating System for web apps. The generated-repo operating pack remains the first implementation proof, but the commercial north star is the loop catalog and diagnostic wedge across all web-app builders.

Add an explicit "doctor pass" product slice after generated-repo source truth is coherent. That slice should define the top-nine opportunity schema, loop taxonomy, scoring rubric, and proof requirements before product UI or ChatGPT app distribution is expanded.

Keep the active source-contract child ExecPlan. It still matters because every later loop depends on trustworthy generated repo instructions, prompts, skills, scripts, and safety boundaries.

After that, prioritize:

1. doctor pass and loop taxonomy
2. BYO execution surface hardening for Codex, API keys, GitHub, and local repos
3. broken-app rescue loop for existing repos
4. customer-safe operating file set
5. explicit generated repo agentic bootstrap
6. worker-led lane journey
7. ChatGPT app or MCP distribution only after the loop contracts are stable

## Watchpoints

Do not let the product become a course about agents. Sell diagnosis, execution loops, and proof. Teach the operating model inside the workflow.

Do not claim autonomous repair across arbitrary repos until the mature-repo audit and safe patch path exist.

Do not blur consent boundaries. A customer must explicitly connect the account, repo, credentials, and execution mode used by any loop.

Do not let every possible loop launch at once. The catalog can be broad, but the first monetized loops should be the ones with obvious buyer pain and clear proof: goal pass, broken-app rescue, design loop, billing/auth hardening, and release proof.

Do not make ChatGPT Apps SDK distribution a blocker for the core business. The loop engine should work through the web app, generated repos, and local or cloud Codex before becoming a ChatGPT app.

## Source Evidence

- Official Codex config reference: project-scoped `.codex/config.toml` exists, but Codex loads project-scoped config only when the project is trusted; Codex also has app/connector feature flags, MCP server config, and model provider configuration.
- Official Apps SDK quickstart: ChatGPT apps expose MCP tools and optional UI resources that ChatGPT can drive.
- Official Apps SDK review guidance: authenticated apps need reviewable credentials, privacy disclosures, accurate tool annotations, and reliable test cases.
- Ship by Sunday current repo: the app already contains optional Codex app-server routes, a settings connection card, and tests for managed ChatGPT login, rate-limit reads, account polling, logout, and generation.
