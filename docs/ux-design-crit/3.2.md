# Lesson 3.2 UX Critique: Map the Repo and Starter

## Outcome Context

### Product goal

`Ship by Sunday` needs to turn the abstract build brief from `3.1` into grounded implementation momentum. Lesson `3.2` is the bridge between deciding what to build and touching the real codebase, so it has to reduce setup ambiguity fast without making repo orientation feel like a side quest.

### Surface goal

Lesson `3.2` should help the student open the right repo, confirm the app can boot locally, identify the relevant env file locations, and locate the first route or screen where their first slice will land. When they leave, the next Build steps should feel anchored in real files, not in guesswork.

### Business model

This is a premium guided execution product. The repo-orientation lesson has to make the system feel operationally trustworthy. If students hit vague setup instructions, fake completion, or blocked completion here, confidence drops exactly when the product is asking them to start building for real.

### Business metrics that matter here

- `3.1` to `3.2` start rate
- `3.2` completion rate
- time from `3.2` load to first successful local boot
- percentage of `3.3` and `3.4` starts with accurate startup command and entrypoint notes
- support signals around “I do not know where to start in the repo”
- drop-off rate between `3.2` and `3.3`

### Assumptions and confidence

- Assumption: the core user entering `3.2` has already chosen a starting path in `3.1` and expects `3.2` to make that path feel concrete.
- Assumption: the main value of this lesson is not educational content by itself, but the confidence transfer that comes from tying the next Build steps to actual files and commands.
- Assumption: students may be using either a template repo or an existing repo, so the lesson should narrow attention rather than rely on one exact codebase shape.
- Confidence: high on the structural UX issues because they are visible in the lesson contract, completion logic, and shared workbench shell. Medium on how often each issue is felt in practice because this pass did not include authenticated browser QA with live student states.

## Problems I Notice

### 1. The lesson appears structurally impossible to complete when the coach video is still pending.

Lesson `3.2` sets `requireReadyVideoForCompletion: true`, and completion logic adds a required `Lesson video is attached and ready` task whenever that flag is on. But the lesson coach content is created with `createPendingLessonCoach(...)`, which sets the video status to `pending` by default. That means the lesson can fail completion even if the student has finished every repo task correctly.

Impact:

- Students can do the real work and still get blocked by a system requirement unrelated to their effort.
- The product risks feeling broken instead of demanding.
- Drop-off here would be especially expensive because it happens at the first live build execution step.

### 2. The workbench tells the student to “open the code workspace” without actually helping them cross that context gap.

The `External workspace` card is only a sentence. It does not show the repo path, provide a copyable open command, surface the chosen build path from `3.1`, or give a direct “start here” file target. The user is told to switch contexts, but the product does little to reduce the friction of that switch.

Impact:

- The page creates an action boundary without enough affordance to cross it quickly.
- Students are more likely to bounce into their editor and start wandering instead of following a tight orientation flow.
- The product feels less software-guided than the promise suggests.

### 3. The lesson can be “completed” with shallow or even inaccurate repo evidence.

The required fields are low-validation: any non-empty `startup_command` text passes, and any non-empty `repo_map_notes` string passes. The checklist also records checked items rather than verified evidence. A student could save `npm run dev` and a vague note like “env in .env, route in app folder” and still satisfy the UI.

Impact:

- The artifact can look complete while being weak or wrong.
- Later lessons inherit bad setup assumptions and convert them into bigger implementation confusion.
- The course rewards form fill-in more strongly than real repo comprehension.

### 4. The lesson does not translate the `3.1` build brief into concrete repo-orientation guidance.

`3.2` pins the `agent_build_brief` artifact, but the artifact is shown as generic context rather than as an operational brief for what to inspect first. The student has to infer how their chosen path and first slice map to the repo exploration task.

Impact:

- The transition from planning to implementation still feels discontinuous.
- Students may orient around the whole repo instead of the route or screen that matters for their first slice.
- The system misses a chance to show that prior artifacts actively drive later execution.

### 5. The focus-mode workbench puts too much passive content ahead of the capture step.

The page stacks `Watch first`, `External workspace`, `Run this sequence`, optional transcript/resources, pinned artifact context, and only then the actual input fields. For a lesson whose value is mostly in capturing concrete repo evidence, that vertical order makes the working portion of the page feel delayed.

Impact:

- The lesson feels more like content consumption than operational setup.
- Students may watch, scroll, and scan without quickly starting the capture loop.
- On laptop screens, the form can end up far enough down the page that the task feels heavier than it is.

### 6. The “Env files + first slice entrypoint” textarea collapses two different thinking jobs into one artifact.

Environment file locations and first-slice entrypoints are related, but they serve different purposes. One is setup orientation; the other is implementation targeting. Combining them into one freeform textarea makes the saved artifact less structured and less reusable in later Build lessons.

Impact:

- Students may capture one half well and skip the other.
- The artifact becomes harder to scan later when they need a quick reminder.
- The next lesson receives an imprecise handoff instead of a crisp repo map.

## Solutions I Recommend

### 1. Remove the hard completion dependency on video readiness for this lesson.

What to change:

- Stop gating lesson completion on `requireReadyVideoForCompletion` for `3.2`, or treat missing video as a content-ops warning rather than a student-facing blocker.
- If video availability matters operationally, surface it in internal QA or author tooling instead of the learner objective task list.

Why it solves the user problem:

- It ensures the lesson can be completed based on student work, not content-publishing state.
- It removes a hidden system failure mode at a critical trust point.

How it supports business growth:

- It reduces avoidable churn and support load in the first live Build lesson.
- It protects confidence in the course as a dependable guided system.

Trade-offs or risks:

- Students may complete the lesson without watching the intended walkthrough.
- If the video is important, the product should encourage it more explicitly in the workbench copy instead of relying on a hidden gate.

How to validate:

- Confirm that a student can complete `3.2` with correct repo evidence even when video status is pending.
- Track whether completion rate improves after removing the gate.

### 2. Turn the “External workspace” card into an action bridge instead of a reminder.

What to change:

- Show the chosen build path from `3.1`.
- Add copyable commands or links such as repo open command, startup command placeholder, and first route target.
- If the template path is selected, surface the template repo URL or starter-specific next step.
- If the custom path is selected, tailor the card copy to existing-repo orientation.

Why it solves the user problem:

- It reduces the friction of leaving the lesson and entering the editor.
- It turns the lesson from “go do setup somewhere else” into a guided handoff.

How it supports business growth:

- The product feels more premium and more software-guided.
- Faster repo orientation should improve continuity into tooling and provider setup.

Trade-offs or risks:

- The card becomes more dynamic and slightly more implementation-heavy.
- It needs careful handling for users whose repo shape differs from the default.

How to validate:

- Watch QA users go from `3.2` to local repo orientation and note time-to-first-editable-surface.
- Check whether fewer students ask where to open or what to inspect first.

### 3. Replace vague freeform completion with structured evidence capture.

What to change:

- Split the repo artifact into tighter fields such as:
  - package manager
  - startup command
  - env file paths
  - first route or screen path
  - optional note for setup caveat
- Add format-aware validation for command and path fields.
- Consider a checkbox like `I saw the app boot locally` tied to the startup step.

Why it solves the user problem:

- It makes the lesson artifact more honest and more reusable.
- It helps students confirm the right evidence instead of typing generic notes.

How it supports business growth:

- Better setup artifacts reduce downstream build confusion.
- Support can diagnose blockers faster from structured notes.

Trade-offs or risks:

- More fields can feel slightly more rigid.
- The product should keep the total capture burden small so the lesson still feels like an orientation pass, not paperwork.

How to validate:

- Review saved `repo_orientation_ready` artifacts for specificity and accuracy.
- Compare later Build blockers before and after structured capture is added.

### 4. Use the `agent_build_brief` to pre-focus repo orientation around the first slice.

What to change:

- Add a small “Based on your build brief, inspect these first” card above the repo capture fields.
- Translate `3.1` decisions into repo-orientation prompts such as which route, provider, or surface to find first.
- If the path is template-based, point to the starter surface. If custom, point to the likely app entrypoint or feature area.

Why it solves the user problem:

- It makes `3.2` feel like the direct continuation of `3.1`.
- It narrows repo exploration to the files that matter now instead of the whole codebase.

How it supports business growth:

- Stronger continuity makes the course feel intentionally sequenced.
- Students should arrive in `3.3` and `3.4` with a clearer mental map.

Trade-offs or risks:

- Inference can be wrong for highly custom repos.
- The UI should frame this as a starting suggestion, not a guaranteed file path.

How to validate:

- QA whether students can name the first file or route they need within a few minutes of entering the lesson.
- Review whether saved entrypoints align better with the chosen first slice.

### 5. Move the capture fields higher and collapse passive support content by default.

What to change:

- Keep the video surface visible, but move the input fields above transcript/resources and possibly above the full checklist card.
- Convert transcript/resources into secondary expandable sections.
- Preserve the sequence, but prioritize action over reading once the student has watched or chosen to skip.

Why it solves the user problem:

- It makes the operational part of the lesson feel immediate.
- It supports a faster watch-then-do loop.

How it supports business growth:

- Faster action reduces the chance that Build feels bloated.
- The lesson better matches the promise of a guided sprint.

Trade-offs or risks:

- Some students benefit from transcript-first learning.
- The page should not bury the walkthrough completely; it just should not dominate the default reading flow.

How to validate:

- Measure time from page load to first field interaction.
- Run browser QA on laptop-height viewports to confirm the form starts within the first meaningful scroll.

### 6. Split the repo map artifact into setup notes and slice entrypoint notes.

What to change:

- Replace the combined textarea with two fields:
  - `Env files and setup paths`
  - `First slice route or screen`
- Show these as separate artifact preview rows so later lessons can reuse them cleanly.

Why it solves the user problem:

- It reduces cognitive mixing between orientation and implementation.
- It creates a cleaner artifact for later reference.

How it supports business growth:

- Cleaner downstream context improves the value of the guided Build sequence.
- The artifact becomes more legible in support and QA flows.

Trade-offs or risks:

- Slightly more UI surface.
- Students with simple repos may feel the distinction is obvious, so the copy should stay concise.

How to validate:

- Review whether later lessons reference these notes more easily.
- Check whether students more consistently capture both setup and entrypoint details.

## Trade-offs and Decisions

- Decision: prioritize fixing the completion gate first because it is a trust-breaking blocker, not just a polish issue.
- Decision: keep `3.2` lightweight. The goal is not deep repo documentation; it is enough evidence to prevent random prompting in the next lessons.
- Decision: prefer structured capture over long freeform notes. This lesson’s artifact needs to be reusable later.
- Trade-off: more structure can feel less flexible, but here that is an acceptable cost because early Build confusion is more expensive than slight formality.
- Trade-off: dynamic path-specific guidance adds implementation complexity, but it pays back by making `3.1` and `3.2` feel like one continuous system.

## Priority Plan

### P0

- Remove or bypass the video-ready completion gate for `3.2`.
- Verify the lesson can complete successfully from valid student work alone.

### P1

- Turn the external workspace card into a concrete action bridge with path-specific guidance.
- Move the capture fields higher so the lesson becomes action-first.

### P2

- Replace the generic freeform repo notes with structured evidence fields.
- Split env/setup notes from first-slice entrypoint notes.

### P3

- Add smarter translation from `agent_build_brief` into “inspect these first” repo hints.
- Improve artifact preview so the saved orientation notes are easier to reuse later.

## Validation Plan

- Run authenticated browser QA through `3.1` to `3.2` and confirm the lesson is completable with the current content state.
- Test both template-path and custom-path students to see whether the external workspace bridge is specific enough in each branch.
- Review a sample of saved `repo_orientation_ready` artifacts for command precision, real file paths, and first-slice clarity.
- Measure `3.2` completion rate and `3.2` to `3.3` continuation after the completion-gate fix.
- Collect support and QA notes specifically for “I do not know where to start in the repo” and “I completed it but cannot move on.”

## Narrative Summary

Lesson `3.2` has the right strategic job: convert the Build brief into real-codebase confidence before tool and provider setup begins. But right now the experience is too easy to complete dishonestly and may also be impossible to complete honestly if the lesson video is still pending. The page asks the student to switch into their editor, yet gives too little help for that context jump, and it underuses the `3.1` build brief that should be steering repo exploration.

The strongest version of this lesson is a short, high-trust orientation pass: confirm the app boots, capture the right paths, identify the first surface for the slice, and move on. That means the product should remove content-publishing blockers, bridge directly into the repo, and demand more concrete evidence than a generic text note. If `3.2` becomes that crisp, the rest of the Build block starts from confidence instead of drift.
