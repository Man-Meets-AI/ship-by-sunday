Lay of the Land

Web projects use a bunch of Lego blocks that are called packages, and
that's what this folder is. They're called node_modules, but you could
just think of them as Lego blocks. There's going to be a manager that
manages those Lego blocks. Used to be that people would fight over this,
but it's more important just to use whatever AI is accustomed to using.

Important Files

We have a couple important files that the AI will likely end up asking
you about, and it's just good to know, so I'll give you a quick
overview. The environment files are essentially a list of your passwords
for different accounts. When you're building your app on your computer,
that's called the local environment, and you'll have that list of
passwords there. When you actually get it off your computer and onto the
internet, your list of passwords will be on the company that's
responsible for hosting your site, which is Vercel.

Knowing these few things will make it a lot easier when you're prompting
your way around the codebase. You can think of it as just a bunch of
different files and different folders. Every app does a few things:

- It needs to be able to authenticate, which means it knows that it's
  who you are versus the next person.
- It needs to be able to authorize, which means it knows, "Okay, we know
  who you are, but are you able to have access to this part of the app?"

Apps' databases are just giant spreadsheets that use that authentication
part that we talked about to let you see information or not see
information. You have ways of getting new information on the page;
that's data fetching. You have something that's called state management,
which is, if something changes on another computer (let's say your
friend's looking at the same screen), does yours need to change as well?
Those are all small details, but I think it's good to at least know the
terms.

And it uses something called components, which, if you're familiar with
Figma, are just reusable pieces of code. If you went on amazon.com,
you'd notice that they have a nav bar; that nav bar looks the same in
most places. Maybe there's one or two changes depending on if you're
shopping for groceries or not, but they're not rewriting that code over
and over and over again. There's one component and then maybe a few
changes within it.

As far as styles go, we're going to be using something that's called
Tailwind. Before Tailwind, you'd have to write a bunch of code in a
language called CSS, which was a cascading style sheet. You don't really
need to know that, but that's just something that you would point out to
the coding agent if you were trying to make style changes.

PLAN Mission-Control Lesson Layout System

Summary

- Replace the current ProductShell plus monolithic LessonPage with a
  product-only workspace system that matches the Figma dark shell, keeps
  the existing palette as a light-mode option, and covers /mission plus
  all lesson routes in one implementation wave.
- Keep layouts registry-driven from app/lessonRegistry.ts: mission stays
  fixed, each lesson keeps its current shell as the default view, and
  every non-mission lesson supports a client- side split/focus override
  plus collapsible objective/coach chrome.
- Keep marketing pages out of scope. This refactor applies to protected
  product routes only.

Implementation Changes

- Introduce a product-scoped theme provider for protected routes only.
  Default to dark, persist the choice in localStorage as sbs:theme, and
  expose the toggle in the top HUD. Do not add next-themes; use a
  lightweight data-theme attribute and semantic CSS variables.
- Convert hardcoded protected-route colors into semantic tokens for
  background, surface, border, HUD, rail, text, muted text, and accent
  states. Light mode maps to the current palette. Dark mode maps to the
  Figma shell, including the dark chrome, translucent panels, blue
  active accents, and wider workbench proportions.
- Do not block shell work on exact Figma font sourcing. Use the current
  loaded brand fonts plus a mono chrome style for HUD, coach, and
  workbench labels until exact font assets are available.
- Replace ProductShell with a shared ProductWorkspaceShell that owns the
  top HUD, route nav, block progression, progress count, theme toggle,
  split/focus controls, coach toggle, and bottom skill rail. /mission,
  /lesson/[lessonId], /artifacts, and / settings all consume this shell;
  only /mission and lesson bodies get redesigned in this pass.
- Redesign /mission as the Figma-style mission control home: 4 block
  cards, registry-driven block state, direct entry to the next available
  lesson, and the bottom skill rail. Use registry truth for progress, so
  the HUD denominator becomes 26 lessons plus the separate mission
  screen.
- Promote the Figma dark-shell background and block art into checked-in
  assets under public/ so the product UI does not depend on expiring
  Figma URLs. and resources payloads. Missing content renders
  intentional
- Keep shell, coachMode, and panelDefaults as the default layout seed.
  Persist per-lesson UI chrome overrides in localStorage as
  sbs:lesson-ui:. Do not store layout preferences in Convex.
- Replace the monolithic lesson renderer with LessonShellSplit,
  LessonShellFocus, and WorkbenchRenderer. The shell owns layout only.
  The workbench owns lesson interaction. Pinned artifacts move out of
  the shell sidebar and become inline context cards or readonly fields
  inside the workbench.
- Implement one renderer per workbench type instead of one giant field
  switch: guided_form, score_table, collector_board, capture_upload,
  scope_split, brief_assembler, console_checklist, tracker_log, and
  external_workspace.
- Back those workbench renderers with reusable field controls for text,
  textarea, select, toggle, table, board, readonly, and upload
  placeholder states.
- Add a stable UploadFieldValue object shape for image_upload and
  video_upload fields so layout work does not need to change when
  storage lands. This phase only needs the renderer contract and local
  preview or empty states; durable student upload storage remains a
  separate implementation dependency.
- Keep Convex lesson progress, autosave, completion, and artifact
  preview flows intact. getLessonState only needs to return the richer
  registry payload. No schema migration is required because fieldValues
  already accepts objects.

Public Interfaces / Types

- LessonConfig gains coachContent with typed video, transcript,
  examples, and resources.
- PersistedFieldValue expands to include an UploadFieldValue object for
  image and video workbench fields.
- LessonPage stops owning layout details directly and instead passes
  lesson data, field values, save/complete actions, and pinned artifacts
  into LessonShell* plus WorkbenchRenderer.

Test Plan

- Run pnpm run typecheck and pnpm run build.
- Manually QA /mission, /lesson/1.1, /lesson/1.5, /lesson/2.4, /
  lesson/3.5, and /lesson/4.3 to cover mission, split, focus, upload,
  external workspace, and tracker layouts.
- Verify dark is the default, the theme toggle persists across refresh
  and navigation, and light mode reuses the current palette without
  broken contrast.
- Verify split/focus/coach state persists per lesson, defaults come from
  the registry, and switching views never drops autosaved field values.
- Verify empty coach content, missing uploads, and unhosted media show
  intentional placeholder states instead of blank panels or runtime
  errors.
- Verify HUD progression, bottom skill rail, next/back navigation, and
  progress counts all reflect registry truth on mission and lesson
  routes.
- Verify tablet and mobile collapse behavior: HUD stays usable,
  objective and coach panels collapse cleanly, and focus mode keeps the
  workbench primary.

Assumptions

- This first implementation wave includes the mission/home redesign plus
  lesson shells; marketing pages stay unchanged.
- Video hosting, transcript files, examples, and download URLs are not
  blockers for the shell refactor; the UI ships with typed content slots
  and graceful empty states.
- Typography parity is secondary to color, layout, and interaction
  parity for this pass.

Whats NPM / PNPM / BUN? 

The PM stands for package manager. Think of a package manager as an app
store for code people have already written. Instead of using a website
to look for the apps, you just tell the package manager to install the
package you want. Package = code already written. Theres packages for
how to handle timezones, how to show the weather on your page, you name
it!

NPM is the old one. PNPM is a newer one. BUN is the newest one. I notice
that most Coding Agents prefer using PNPM, so dont bother asking it to
use something it prefers using.
